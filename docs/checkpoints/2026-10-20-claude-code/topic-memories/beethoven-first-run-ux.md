Greg tried Beethoven 10.0.0 as a student on the real grid (2026-10-01) and rejected the first-run flow. What he wants, in his order: prerequisites first (grid account, Claude Pro/Max; he believes a GitHub account linked to Claude is mandatory, which is being checked), then the GlobalProtect VPN (portal address `protect.wayne.edu`), then the portal with `ondemand.grid.wayne.edu` as the default and a way to type another, sign-in as close to one click as possible, no terminal window for the student, the Claude sign-in without hunting for windows, and a visible account of the worker starting. He saw "no indication that a worker was really started" although the job queued six minutes and came online (job 40523644).

**Why:** he wants it "streamlined and seamless", "as much automatic" as possible, no window switching, a token-free success message, and "PROFESSIONAL LIKE APPLE".

**How to apply:** every wait must show what is happening and how long it usually takes; one idea per screen, one primary button, no internal words; the panel should stay in view across tabs. He asked for Beethoven to prefill the university AccessID and password: my position is that Beethoven must not handle the university password (browser password manager instead); present him the facts and let him decide, see [[ashley-compliance-boundary]]. The VPN cannot be driven by an extension; detect and guide. Design work: workflow wf_7b9c455f-69b, spec at scratchpad v11/SPEC.md; next build is 11.0.0. Related: [[students-see-no-internals]], [[ashley-bridge-project]].

**Second message, same day:** the panel is the product. It stays a side panel and becomes an interactive home: live connected status, a button to reopen the existing Claude session and one for a new one, Stop/Start, other easy-access buttons, animations, cream style like the website (he finds the current UI "old school"). Log hidden behind "Show log", expanding in place. A brief demo of what the app can do. The agreement must NOT require scrolling: a tick that they read it, with an optional "Show TOS" expander (his decision as licensor; this reverses the scroll gate enforced in 10.0.0). Close the OnDemand tab automatically after sign-in if feasible. Make sure Remote Control is enabled by the flow and nothing depends on an ssh key (the cluster tool uses no ssh; only the portal's own Shell app does). He says GitHub was the only one-click option he saw when authenticating Claude.

**Third message:** he suggested replacing the portal-tab dependence with "a persistent ssh key that maintains the connection as long as the browser window was open". A Manifest V3 extension has no raw sockets, so an ssh connection needs a native host or a bridge; his intent is what matters: the student never tends a tab, and if the grid needs a tab, Beethoven opens it by itself from the button that needs it ("connect a Claude session"). "Make it intuitively designed and natural to use": the student thinks connect, open my session, stop; never tabs, portals or shells.

**Fourth message:** "Can you integrate setting up an ssh key into the first connect and save it to the browser?" Decision carried into the build: integrated into the first Connect, yes (the student only types the grid password into the university's own terminal page; Beethoven then types the one setup line, closes the tab, carries on); saved in the browser, NO: an extension cannot use an ssh key (no sockets), the key that matters lives in the student's grid account, and a browser copy would be an unused credential opening a university account without password or second factor. The key is made on the grid in its own file and restricted with from= to the OnDemand server's address. Greg was told this; if he reaffirms wanting a browser copy, explain again that it has no use before doing anything.

**Fifth message:** the VPN is unreliable; the grid accepts ssh from outside once the second factor is set up; he wants browser-based ssh under the hood so OnDemand is eliminated or used once (a pop-up or typing in a terminal is acceptable to him). Established 2026-10-01 from outside the VPN: grid.wayne.edu:22 is OpenSSH 7.4, offers publickey, password, keyboard-interactive; host key RSA only (SHA256:kLTz1xK6anQ1denM+31kDEryQtgan2P76r9aLno+K3s), ciphers aes-ctr only, MAC hmac-sha1 only; Greg's key signs in with no second-factor prompt. A browser has no sockets, so this needs a relay (WebSocket to TCP 22; a Cloudflare Worker can do it) plus an ssh client on WebCrypto in the extension; with that, a browser-held non-extractable key DOES have a use (this revises the earlier 'a key in the browser is useless' answer, which was true only without a relay). Prototype and security review: workflow wf_91ebd691-8df, output scratchpad v11/ssh (design in v11/ssh/design/SSH_DESIGN.md). Open decisions for Greg: whether Beethoven may receive the typed password (variant A, no VPN ever) or enrol the key through OnDemand once (variant B); telling C&IT that student sign-ins would arrive from a lab-run relay on Cloudflare addresses.

**Sixth message:** after a student described connecting with ssh + password + Google Authenticator, Greg wrote "This is a more simple way for students to connect": his preference is ssh sign-in from Beethoven with AccessID, password and code, no VPN. The university's tutorial (KB 20242) says the code is set up in OnDemand's 2FA Setup app on the VPN, so that one visit remains for a student who never set it up. See [[grid-ssh-second-factor]].

**Seventh message (2026-10-02), the 12.0 order:** incorporate the phone-based VPN route into the guided setup (a QR code to the GlobalProtect iOS instructions, a link/QR to KB 20242 for the grid's Google Authenticator code, Beethoven guiding the Authenticator scan of the university's QR); the extension tries the ssh no-VPN path FIRST (password and code the first time, then a key for seamless use); a local helper is now ALLOWED but as the LAST resort after exploring browser-only bridges (another store extension such as Google's Secure Shell, Cloudflare, web ssh); build end to end, test, make the 12.0 release package with detailed install and use instructions and a list of every new account or subscription needed. Build workflow wf_571a9513-d73; outputs under scratchpad v12/build and release/12.0.0 when done. Related: [[beethoven-browser-ssh]].

**Eighth message (2026-10-02):** asked whether the helper could be compiled in the browser or shipped with the extension to stay self-contained; answered: an extension cannot run a program it contains and nothing in a tab can open a socket, so the helper ships INSIDE the package as script hosts (PowerShell via a .cmd on Windows, Perl on macOS and Linux) that the student saves and installs once with no admin rights, no compiler, no signing account, no website download. Greg also decided: Windows Hello / Touch ID protection of the key is OPT-IN (default off); run the build as parallel as possible. Build restarted as wf_fef877f0-ef2 (exploration and five build streams at once, then verify, then two fixers and an assembler); outputs under scratchpad v12/build and release/12.0.0.
