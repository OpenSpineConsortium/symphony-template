Prototype of 2026-10-01 (workflow wf_91ebd691-8df; code and logs in the session scratchpad under v11/ssh; design in v11/ssh/design/SSH_DESIGN.md). An ssh client written on WebCrypto with no dependencies runs in Chrome and in a worker, interoperates with OpenSSH configured like the grid and with asyncssh (password, prompted second factor, non-extractable browser key kept in IndexedDB), and completed one pinned, unauthenticated handshake with the real grid.wayne.edu. A WebSocket-to-ssh relay with single-use signed tickets ran under workerd and as a 59-line Node program. The security review found four fixable flaws (send path not closed after a host-key mismatch, no handshake timeout, an AES-GCM counter that never carries, strict key exchange advertised but not enforced) and no fundamental one. Nothing has run against the real grid with a credential.

**Why it is not in 11.0.0:** recommendation is to ship it as 12.0.0, ssh as the main path and the 11.0.0 portal path as fallback, and only after hpc@wayne.edu answers in writing.

**How to apply:** facts that bound the design: Wayne State's personal-devices standard says "Multi-factor authentication is required for all remote access", and a browser key skips the grid's code; the password standard says never save passwords in browsers or programs (typed once, never stored is the only acceptable form); Cloudflare's self-serve agreement forbids using Workers for "a virtual private network or other similar proxy services", so the relay should be a small lab machine with one fixed address (which also allows a from= restriction); the grid key entry must be limited by a forced command to Beethoven's own verbs and must never be able to sign a worker in to Claude; the grid's code can only be set up in OnDemand's 2FA Setup app on the VPN ([[grid-ssh-second-factor]]); WSU KB 20254 says the grid makes an ssh key pair automatically at a student's first login. Decisions waiting on Greg: may Beethoven receive the typed password and code; may a key that skips the code be enrolled; how often to re-ask (30 days recommended); where the relay runs; send the question to hpc@wayne.edu (a draft was given to him 2026-10-01). Greg's stated preference: ssh with password and code, no VPN ([[beethoven-first-run-ux]]). Related: [[ashley-bridge-project]], [[ashley-compliance-boundary]].

**Correction (2026-10-02):** my 'no fourth option' claim was too strong. An Isolated Web App (IWA) with the Direct Sockets API gets a raw TCPSocket to grid.wayne.edu:22 with no relay and no native helper, so it is the one browser path that meets all of Greg's constraints. Its price: it is not an extension (no side panel, toolbar button or content scripts; a standalone app), it is not distributed through the Chrome Web Store, and on an unmanaged laptop it installs only by enabling developer flags and loading a signed .swbn through chrome://web-app-internals (or by enterprise policy); desktop Chrome only. From an isolated-app:// origin the IWA probably cannot read the OnDemand portal (CORS), so first-time key enrolment would go through the 11.0 extension or a one-line paste in the OnDemand terminal. Greg pasted an AI-written proposal for this on 2026-10-02 and asked for my view; a feasibility spike on his own machine was offered.

**2026-10-02, two more ideas from Greg:** (1) iPhone GlobalProtect + hotspot as the one-time VPN for the laptop: phones do not pass hotspot clients through their own VPN tunnel as a rule, so this is not dependable; the sanctioned one-time routes are GlobalProtect on the laptop for that session, or doing the 2FA setup on the phone itself and pasting the laptop's public key into the OnDemand terminal there. (2) Touch ID / Windows Hello / passkey instead of a master password for the browser key: right mechanism is WebAuthn PRF wrapping the ssh key (prompt once per app launch); a FIDO-backed sk- ssh key would be better still but the grid's OpenSSH 7.4 does not accept sk- key types; PRF support varies by OS and authenticator and must be tested per device, with a PIN or passphrase fallback. Both to be folded into the IWA feasibility spike if Greg says go.

**2026-10-02, Greg's decision:** build the web-app (Isolated Web App + Direct Sockets) version and test it in parallel with 11.0; offer the PHONE route for the one-time setup (he verified GlobalProtect for iOS + Safari opens OnDemand's 2FA Setup app; the page warns that running it again destroys existing authenticator credentials). Feasibility spike: workflow wf_7b3b8dff-1e2, everything under scratchpad v12/iwa (REPORT.md, STUDENT_STEPS.md when done); nothing in the repository. Open after the spike: Greg's own test (enrol his browser key through OnDemand, then one key sign-in from the app with no VPN), and the full 12.0 build.

**Spike result (2026-10-02, wf_7b3b8dff-1e2):** the web app WORKS on Chrome 154 stable and Chromium 153 in developer mode: raw TCPSocket inside a signed IWA, key sign-in to a grid-like local sshd, one pinned credential-free handshake with the real grid from inside the app with no VPN. Install = 12 steps via chrome://flags (two flags) + chrome://iwa-dev, permanent 'unsupported feature flag' bar, manual updates, breaks on Reset all; no store or consumer channel on Windows/Mac (policy install ChromeOS-only; managed Windows announced for Chrome 161 ~Jan 2027). Verdict: opt-in pilot beside 11.0, not the main path. Passkey PRF works on https and extension pages but Chrome refuses WebAuthn on isolated-app:// so the app needs an https frame from a lab domain: the security review's one BLOCKER. Nine majors incl. gate verbs run python3 on warrior, no job cap on the gate, shared-copy writability unchecked, CTR receive stall, unencrypted signing key in tree. Not proven: a key sign-in to the real grid (Greg's test G1, 15 min, written in REPORT.md section 7), phone paste into the OnDemand terminal (G2), real Hello/Touch ID (G3), Mac.
