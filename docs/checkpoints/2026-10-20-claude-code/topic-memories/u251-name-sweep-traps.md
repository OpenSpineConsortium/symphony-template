Three things make a repo-wide sample-name rename in `u251-xenograft-murine-RNASeq-study` unsafe. Established
2026-09-27 while scoping one that Greg then called off.

1. **`N1` and `N2` in `ANALYSIS/power/` and `ANALYSIS/spread/design/` are null hypotheses, not samples** -- e.g.
   "Null N1 : contralateral barcode counts ~ Multinomial(D, p_core)", and "0.70, N1"/"0.60, N2" are power targets. A
   token sweep of `N2`->`N269B` would silently convert a hypothesis label into a sample name. It does not even split
   by directory: `ANALYSIS/power/pilot/` uses `N2` in the sample sense.
2. **`PREREG*.md` and `TARGETS.md` are hash anchors.** Their SHA-256 is recorded inside result files as
   `prereg_sha256` and quoted in the manuscript. Editing their text breaks the tie between a result and its
   pre-registration.
3. **Result files carry `_sha256` stamps.** `MANUSCRIPT_NOA/results/*.json` and `SLIDES/figures_cns/v5_data/*` are
   outputs; renaming keys by hand invalidates the integrity field that makes them auditable. They can only be
   regenerated by rerunning the pipeline.

Also: `CDKN2A`, `CDKN2B`, `GCN2` contain `N2`, and `hgnc_complete_set.txt` / `MGI_MRK_List1.rpt` are third-party
reference downloads that must never be edited.

**Why:** the recurring failure mode in Greg's projects is a value that is wrong but plausible; each of these would
have produced exactly that.

**How to apply:** treat sample labels as fixed and carry correspondence in an explicit generated key
([[u251-multiomics-sample-pairing]]). If a rename is ever actually required, scope it by an explicit per-file allow
list, exclude the three categories above, and regenerate outputs rather than editing them.
