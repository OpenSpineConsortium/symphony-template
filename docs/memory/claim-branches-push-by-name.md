A claim branch is made with --no-track and every push names it, because git's push.default decides where a push goes and the push guard cannot see it.

Made with `git switch -c claude/N origin/<default>`, a claim branch tracks the default branch. Where git's push.default is upstream, or its old name tracking, git sends a push of such a branch to that upstream whatever the command names: `git push -u origin claude/N`, `git push origin claude/N` and a bare `git push` all wrote the default branch, in git's own words `claude/7 -> main`, and never made claude/N, and after a rebase `git push --force-with-lease` forced the default branch. The push guard passed every one, since it reads the command and not git's settings. Under push.default matching, a bare `git push --force-with-lease` forces every branch that has a namesake on origin, and it rewound main to a stale local main. Under git's own default, simple, and under current, the old step was safe.

So the claim skill makes the branch with `--no-track`, the claim push giving it its upstream, origin/claude/N, and names the branch in every push: `git push origin claude/N`, and `git push --force-with-lease origin claude/N` after a rebase. Those landed on claude/N, with main untouched, under all five settings: upstream, tracking, simple, current and matching. A branch made from the checked-out default branch with `git switch -c NAME` takes it as its upstream too when branch.autoSetupMerge is always or inherit, and then its `git push -u origin NAME` wrote main under push.default upstream; so the start pages make their branches with `--no-track` as well. `git push -u origin HEAD` landed on the branch's own name under every setting.

Measured with git 2.43 in scratch repositories with bare remotes on 2026-10-13, after a review of symphony-protocol 0.4.1 found it. A guard that asks git where a push goes would be symphony-protocol's change, not this repository's.
