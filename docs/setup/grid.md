# A job on the WSU grid

A workflow job of this repository can run on Wayne State's grid instead of GitHub's machines, through Beethoven: `tools/grid_runner.sh` in OpenSpineConsortium/hpcworker serves GitHub's own self-hosted runner as a chain of Slurm jobs, and .github/workflows/grid.yml here names the runner's labels, so the command it is given runs on a compute node, in a checkout of the ref, and the output comes back as the job's log and as an artifact. docs/research/wsu-grid-and-github-actions.md says what was measured and weighed before this was built; the owner's thread "Symphony on the WSU grid" decided it on 2026-10-16.

## How it works

GitHub's runners cannot reach the grid: the portal and ssh sit behind the university's VPN and a one-time code, and nothing of the grid's (a password, a key) may sit at GitHub, nor anything of GitHub's on the grid beyond one job's credential (hpcworker's CLAUDE.md). So the connection points the other way, as the grid's CI lane does. On the grid, under the account's own gh sign-in, `tools/grid_runner.sh --start --repo OWNER/NAME` queues a Slurm job on the worker queue the site profile names (reqp/requeue at Wayne State, preemptible; --partition and --qos choose another), 8 hours of wall time unless --hours says otherwise, which, before anything else, queues its own successor (afterany, singleton), so the runner is back after a wall time or a preemption with nobody at the keyboard. In the job the runner runs inside GitHub's own image (ghcr.io/actions/actions-runner as a SIF: the runner is a .NET 8 application built for RHEL 8 and later, which the grid's EL7 nodes are not) with `--containall --cleanenv --no-mount bind-paths`: it sees no home, no lab volume and none of the environment, only its own files on the node's disk and a /tmp there. It is registered for one GitHub job at a time with a just-in-time credential: gh mints it into a mode-0600 file on the node's disk, the runner reads it, listens, runs one job and ends; GitHub removes the registration itself, and the chain deletes one that ran nothing. Registrations stop a margin before the wall time (--margin, 60 minutes unless set), so a job must end within that margin, or the wall time cuts it off and GitHub reports the runner lost.

A workflow job reaches the runner with `runs-on: [self-hosted, grid]` (GitHub adds linux and x64; the chain adds the site's name and what --labels gave it). grid.yml is such a job: one command, typed on the workflow's page or passed by another workflow, run with bash in a checkout of the ref, its output in the job's log and in the artifact grid-<run>-<attempt>, kept 14 days. The runner's container carries git and the runner's own node and no python, so grid.yml sets Python 3.12 up with actions/setup-python unless its python box is unticked; the default command, `bash scripts/check.sh`, then runs the repository's own check there. With --slurm at --start, the host's Slurm client is bound into the container as the worker's is, so a step may queue a job of its own with sbatch.

## What it takes

- A private or internal repository. The chain refuses a public one, as GitHub advises: a public repository's forks could run their pull requests on the grid. grid.yml also runs only while the repository is private and never for a fork's event.
- On the grid: a clone of OpenSpineConsortium/hpcworker under the account, gh signed in there as an administrator of the repository (a just-in-time registration needs one; `gh auth status` says who is signed in), and the site profile wayne, which names the module apptainer/1.2.2, the worker queue and the lab volume. Every command names it with --site wayne; hpcworker reads it with its own awk reader, since the login node's banner bans python3.
- No secret and no token anywhere: not in the repository, not in a job file, not on a command line. The runner's one-job credential is minted on the grid and leaves with the job. The Claude token the repository's own workflows use never reaches the grid, and no Claude workflow runs there: claude.yml, workers.yml and coordinator.yml stay on GitHub's machines.
- No Actions minutes: a self-hosted runner's time is not billed.

## The owner's steps

Everything on the grid is the owner's. Each step, with where to click:

1. Open the grid's shell: https://ondemand.grid.wayne.edu on the VPN, the Clusters menu, then the shell entry.
2. Take hpcworker's current main there: `gh repo clone OpenSpineConsortium/hpcworker` the first time, `git -C hpcworker pull` after.
3. Install the runner's image once: `cd hpcworker && bash tools/grid_runner.sh --install --site wayne`. It prints the install job's number; the job's log is /rs/rs_grp_oschome/$USER/hpcworker-runner/image/install-<job>.log and ends with "installed: runner <version>". A line starting "STOP:" names what the grid refused; hpcworker's docs/OPEN_QUESTIONS.md lists what is not yet measured, and the install job is the first test of most of it.
4. Start the chain: `bash tools/grid_runner.sh --start --repo OpenSpineConsortium/symphony-template --site wayne`, with `--slurm` for sbatch inside a step, and `--hours`, `--margin`, `--cpus`, `--mem` or `--gres` to size it. It prints the job's number and the labels a workflow names.
5. See the runner: https://github.com/OpenSpineConsortium/symphony-template/settings/actions/runners lists it as grid-wayne-<job>-<n>, Idle, while the chain's job runs and is registered. Between two registrations, or while the chain's job waits in Slurm's queue, the list is empty and a job waits for the next registration, up to 24 hours.
6. Run a job: https://github.com/OpenSpineConsortium/symphony-template/actions/workflows/grid.yml, press "Run workflow", keep or change the command, press the green "Run workflow" button. The run's page shows the log as it comes; the artifact grid-<run>-<attempt> is under Artifacts at the bottom of the run's summary page.
7. Watch the chain: `bash tools/grid_runner.sh --status --site wayne --repo OpenSpineConsortium/symphony-template`, which names the runner's folder first; its logs are /rs/rs_grp_oschome/$USER/hpcworker-runner/OpenSpineConsortium-symphony-template/runner-<job>.log.
8. End it: `bash tools/grid_runner.sh --stop --site wayne --repo OpenSpineConsortium/symphony-template`; a GitHub job in flight finishes first, and `--now` cancels it too.

## What to expect, and what is not yet measured

A job waits while the chain's Slurm job waits in the queue, and a job that arrives in the seconds between one registration's end and the next waits for the next; GitHub holds a job for a self-hosted runner for 24 hours and then fails it. A job the wall time cuts off fails as "the runner has lost communication": keep each job under the margin. reqp/requeue is preemptible: a preempted chain job is requeued, deletes the registration it left and registers afresh, and a GitHub job that was on it fails. Nothing of this has run on the grid yet: compute nodes reaching ghcr.io and github.com, the container flags on the grid's Apptainer 1.2.2, the runner on an EL7 kernel, Slurm's end time, the chain of jobs and actions/setup-python inside the container are open questions in hpcworker's docs/OPEN_QUESTIONS.md, each with the first test that answers it.
