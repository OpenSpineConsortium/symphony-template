## The PubMed connector does not reach Elsevier

It searches NCBI's PubMed and nothing of Elsevier's, and it has no sign-in, so it cannot carry the institution's access. Its seven tools in Claude's connector directory are search_articles, get_article_metadata, find_related_articles, lookup_article_by_citation, convert_article_ids, get_full_text_article and get_copyright_status.

- It gives the citations and abstracts PubMed indexes for Elsevier's journals.
- It gives full text only where PubMed Central holds a free copy. The directory names the tool but not its source, so this is inferred.
- It cannot give Scopus's cross-publisher citations and author profiles, the engineering and computing venues PubMed leaves out, or ScienceDirect's subscription full text.

The directory has no Elsevier, Scopus or ScienceDirect connector. Those need the owner's Elsevier key with the institutional token, cleared for private use by the library and Elsevier on 2026-10-19 (notebooks.md).

One click, nothing pasted (the owner, 13:18 UTC: "i want one-click oauth type secret key creation to completely avoid pasting"). Claude Code 2.1.310's own code, read in this thread, shows how its sign-in returns. It listens on http://localhost:<port>/callback, so where the browser runs on the same computer, as with `python3 scripts/tokens.py` on the owner's, the sign-in comes back by itself. Where it cannot, as on a grid node or a runner, Anthropic's page sends the browser to https://platform.claude.com/oauth/code/callback, which shows a code of the form code#state to paste. That paste is the one step left in the grid's sign-in (grid-claude-accounts.md: the panel's accounts login and accounts code words, and Beethoven's paste box) and in the Tokens page's Add a Claude account (tools/token_run.py). On Anthropic's written permission for the owner's apps to handle the claude.ai sign-in (desktop-app-and-llm-agnostic.md, Decisions for the owner, 1), the extension that opened the sign-in, Beethoven or Symphony for Chrome beside the control panel's Grid tab, reads the code and state from the return page's address, hands them on as the paste box does today and closes the tab, so the owner's one action is Authorize. The code is useless to anyone else: the sign-in is PKCE, so only the Claude Code that printed the link, holding its verifier, can exchange it, and only once. The same pickup serves `claude auth login --console`, whose sign-in asks for the scope org:create_api_key and then has Claude Code create an API key itself (it posts to api.anthropic.com/api/oauth/claude_cli/create_api_key and keeps the raw key as its own login-managed key), the full sign-in kept for GitHub's runners, and Add a Claude account. Reading the return page needs a permission the extensions may not hold yet, for which the Chrome Web Store asks a justification, and a version of each privacy statement that names the read, before it ships.

A full sign-in on GitHub's runners is the part to measure (the owner, 13:28 UTC, in the thread on the research loop: "This is unacceptable that this can't happen entirely in Github Actions ... i dont care if its through a paid feature of github"). A setup token is inference only, and Claude Code's code treats any token given by variable as inference only too, so such a run uses the command line on a restored sign-in folder, never the variable, with CLAUDE_CODE_OAUTH_TOKEN and ANTHROPIC_API_KEY unset, since either would take precedence. When Claude Code refreshes a sign-in it keeps the old refresh token unless the server returns a new one, so whether Anthropic rotates the refresh token, and how long one lasts, decide whether the write-back may ever fail; one run at a time per sign-in, by a concurrency group, keeps two runs from racing it, and the file is sealed back through the SymphonyBoard App's token, as token_run.py stores a token in the organization's pool today (tools/sealbox.py). On the grid's runner none of this is needed: the sign-in stays in its folder, and Claude Code refreshes it in place.

The setup step, grid/literature-setup.sh in SchwingNet, runs at the start of each job, on the grid's runner or GitHub's, so it needs nothing from the owner:

1. For runs on the Console key only, since those load no claude.ai connectors, it adds PubMed and bioRxiv by URL with `claude mcp add`. They need no sign-in.
2. Runs on the key leave out Scite, Consensus, Wiley Scholar Gateway and alphaXiv, since signing in to them apart from claude.ai, with `claude mcp login`, means pasting the address the browser lands on back into a prompt. Runs on the subscription reach them through claude.ai.
3. It asks for no key. The subscription needs none. The Console key, for runs where a setting puts it first, is made by Claude Code's own Console sign-in with the one click above, in a sign-in folder of its own on the grid, or kept as a secret for GitHub's runners; Claude Code creates the key in the owner's Console and keeps it in that folder, so nobody sees, types or pastes it, and AI Scientist Pro's launcher points Claude Code at that folder only when the order setting puts the key first (decision 4). Only the Elsevier key and token, which no sign-in can make, are GitHub secrets: the key route of 2026-10-23 carries them to a file on the grid that only the owner can read, and a job on GitHub's runners takes them from its own secrets (decision 3). The owner named them at 14:17 UTC: ELSEVIER_API_KEY and ELSEVIER_INSTTOKEN, since GitHub takes only letters, digits and underscores in a secret's name. Kept once as organization secrets that SchwingNet and symphony-template may read, each serves the key route and GitHub's runners alike, since a job reads its organization's secrets as well as its environment's. A value not saved yet can be saved by the extension from Elsevier's own key page in one click. The token may not be needed on the grid, since Elsevier may recognise it as Wayne State's network, which phase 1 tests; GitHub's runners need it.
4. It adds the Elsevier server, tools/elsevier_mcp.py, written with the standard library alone: Scopus search and ScienceDirect full text by DOI. The server reads the key and token from their private file, never from its command line, which other users of a shared node can see, or from Claude Code's settings. It sends them only to api.elsevier.com, in the headers X-ELS-APIKey and X-ELS-Insttoken, as Elsevier's own client does, and never in a URL.
5. It lists each server's state, so a failed sign-in shows at once.

The credential table in desktop-app-and-llm-agnostic.md names a grid worker's sign-in as the one credential that sits in a plain file; the Console sign-in's folder and the Elsevier values' file are two more on the grid, each of mode 600 in the owner's grid home, and a full sign-in kept as a secret for GitHub's runners would be one more, in GitHub; that table gains their rows when phase 1 makes them.

Five facts from Claude Code's MCP page set this shape. Claude Code fetches the account's claude.ai connectors only under a claude.ai subscription login, never while ANTHROPIC_API_KEY, an apiKeyHelper or a setup token supplies the credential, so a run on the subscription gets the connectors connected once at claude.ai and a run on the key needs servers of its own. A `claude -p` run has no /mcp panel and cannot run the OAuth flow, so each sign-in is made once interactively and the runs reuse it. `claude mcp login` prints the link where no browser is available, as over SSH. Claude Code reads its own credentials, ANTHROPIC_API_KEY among them, as empty in a remote server's url and headers, and strips credential-like variables from the helpers a repository supplies, advising such a script to read its credential from a file, which the Elsevier server does from the start. And a run without a terminal loads a repository's own `.mcp.json` servers without asking: runs on the subscription keep them out by name with `disabledMcpjsonServers`, since a `--strict-mcp-config` run uses only the servers passed to it and so would leave out the claude.ai connectors too (phase 1 confirms this), and runs on the key start with `--strict-mcp-config`, naming only the servers this plan allows.

A server that accepts only claude.ai's own sign-in address stays a claude.ai-only connector, and the setup step names it. A Managed Agents vault would hold the same sign-ins for runs on Anthropic's servers, but the experiments stay on the grid, so it is not needed.

## What AI Scientist Pro is built on

The base, which the owner agreed on 2026-10-25, is Sakana's newest, The Agentic Scientist (arXiv 2610.18933, 13 October 2026; code in SakanaAI/AI-Scientist-v3). It drives a coding-agent harness (Codex, Claude Code, OpenCode or Pi) over a frontier model: parallel workers, each with an ideation agent and an execution agent, then ablation, analysis and writing agents, with an evidence map and a check for unsupported numbers. People set the question, the constraints, the baseline and the rubric, or an agent drafts them for review. It reports reward hacking seen and rubrics tightened, calls reviewer scores a proxy and not evidence, and covers machine learning tasks only.

The AI Scientist v2 (Nature, 26 March 2026) picks its own question from a code template or a topic, runs a tree search over experiments, writes a LaTeX paper judged by an automated reviewer, calls several providers' APIs directly and searches Semantic Scholar for novelty and citations. Its stated limits are inaccurate citations, ideas implemented wrongly and computational experiments only.

v3 is preferred because it works through Claude Code, so the sign-ins above and Claude Code's hooks apply to it as to any session; v2's direct model calls would bypass both. v3's code was not read in this thread: how it calls Claude Code, what it sandboxes and where it searches the literature is the first thing phase 0 checks. The owner's answer was "work through claude code": if phase 0 finds v3 cannot run that way on the grid, its stages are built as Claude Code agents instead, and v2's direct model calls are no fallback.

Where it runs:

- In GitHub Actions (the owner, 13:28 UTC). Long jobs run on the grid's self-hosted runner, which spends no Actions minutes while the enterprise's budget for extra minutes is $0, as the owner said that morning, and every job that touches the corpora stays there, since the data never leaves the grid. GitHub's own runners take short steps, and, once the owner raises that budget, long jobs on synthetic or public data, GitHub's GPU runners among them. Claude Code runs on the owner's subscription by default, signed in as the grid worker is (hpcworker's account folders, grid-claude-accounts.md), and on the Console key only when a setting puts the key first; the grid's node reaches the internet over HTTPS.
- Each campaign is one SchwingNet issue, one branch and one pull request under the claim protocol. Its experiments are grid jobs, each under the owner's word and count, with the size rule on every fetch.
- Its papers stay drafts inside SchwingNet until the provisional is filed, and nothing it writes is submitted.

## The lessons, as checks

The articles agree that long runs fail through premature claims and lost state, not through a lack of intelligence, and Schwartz found in Vibe physics that honesty rules in CLAUDE.md helped only "a little". So AI Scientist Pro rests on checks and files, not on prompts.

| Lesson | Seen in | What AI Scientist Pro does |
| --- | --- | --- |
| Agents call work done or verified too early. | Harnesses; Vibe physics; Claude-shaped science | "Done" is a fixed list of checks, written before a campaign starts, that the agent cannot edit. A claim counts only when a separate checker finds its recorded run. |
| Under pressure they fit the result: tuned plots, reward hacking, the answer the person seemed to want. | Vibe physics; The Agentic Scientist | The evaluation code, the split and the witness frames are outside what it may change. Only the evaluator scores the held-out test, and prompts never name a hoped-for number. |
| A foundational error survives many rounds of self-review. | Vibe physics | A reviewer in a fresh context re-derives each keystone step, as Claude re-proved the zeta result from scratch, and the owner checks the keystone. |
| Ground truth comes from a checker, and from checking the right statement. | Riemann zeta; Fermat | The checker is the recorded evaluation with its intervals. Before any run, a comparison confirms that the split, the metric and the code digest match the registered plan. |
| Memory lives outside the context: progress files, a map of the work, hand-offs. | Harnesses; Fermat; The Agentic Scientist; Claude-shaped science | Each campaign keeps a progress file and a map of its claims in its branch. Every session reads them first, updates them last and commits after each step. |
| One small piece at a time, with a smoke check first. | Harnesses | One hypothesis per cycle; each session runs the block smoke test and reads the progress file before new work. |
| Fixed tools beat an agent's own retrieval and counting. | Agents in biology | Literature and data come through fixed tools: the Elsevier server, PubMed's tools and the data catalog. Every query is logged for re-running, and counts come from the catalog. |
| Check novelty before claiming. | Riemann zeta, 54 papers read first | It searches Scopus and PubMed before a campaign starts and again before writing, citing each paper by DOI. |
| People own the direction, the taste and the last word. | Vibe physics; Claude-shaped science; Fermat; The Agentic Scientist | The owner sets each campaign's question, baseline and rubric and approves its grid jobs. Nothing leaves a draft without the owner. |
| Agents grind, misjudge time, and scale alone fails. | Claude-shaped science; Riemann zeta, 650 failed ideas; Fermat, 6 billion tokens | Each campaign has a fixed budget in cycles and grid hours, with no dollar cap (decision 5), and stops after a set number of cycles without progress. |
| Results vary from run to run. | Agents in biology | Decisive comparisons repeat with fresh seeds and report intervals, as the project's results already do. |
| Mark AI-written work. | Sakana | Every draft records in its front matter that AI Scientist Pro wrote it. |

## What AI Scientist Pro writes

The owner's brief of 2026-10-25, sent while this plan was being written: the textbook site is good but "too verbose and exposes the underlying raw artefacts via links too much", and AI Scientist Pro, "and perhaps any future sessions", should hide the underlying artifacts, embed their figures, relevant text and references, and present "a polished, edited, abridged version which follows a theme". The paper tells the story of an idea: its relation to prior art, its methods, its results against benchmarks, its conclusion and the vision of where the work goes next. It is "packed to the brim with reference", shows most of its information in the discipline's conventional figures, and argues "as definitive, absolute, and revelatory as possible", persuasively but "based on unbiased experimental methods and data". A minute later the owner added that none of the textbook's construction is to be disregarded: its artifacts are, or are to be, tied to specific experiments with CLAIM-compliant ledgers, so that a result can be reproduced in one click once the research loop is packaged and importable.

So AI Scientist Pro works over two layers:

| Layer | What it holds | What readers see |
| --- | --- | --- |
| The raw layer, kept whole | The textbook, its artifacts and figure records, and every run's ledger row, CLAIM 2024 and REFORMS report and provenance (SchwingNet's tools/flow.py and tools/report.py) | Nothing directly: AI Scientist Pro queries it through an embedding index on the grid |
| The paper | One theme told as a story: the idea, prior art, methods, results against benchmarks, conclusion, what it changes and what comes next | The paper alone, with its figures, the relevant text and dense references embedded, never linked out |

How it stays honest while it argues:

- The writer is the idea's advocate, and the evidence stays neutral: the methods, the split and the metric are fixed in the registered plan before any result exists.
- Every number comes from a recorded run, and a number meant for publication from a run whose report passes the publication gate, `tools/report.py check --complete`.
- A sentence the evidence does not carry is cut, not hedged, which is what lets the prose stay definitive.
- Every experiment goes through the same flow as any other run, so each leaves its ledger row and report.

Each figure in the paper carries its run's id in place of a link. Once the research loop is packaged and importable, which SchwingNet #293 begins with the block framework, one click re-runs the run behind any figure; until then a figure record's Re-run issue does it through figure.yml. On 2026-10-25, 33 of the textbook's 99 figure records named the job, script or run behind them, 23 carried a re-run command, and one, the experiments panel of chapter 35, read the flow's ledger, which held two runs, both dry runs on a synthetic bank. Phase 2's check lists the rest so each can be tied to its experiment; until it is, the paper cites it as text and never as a result.

The Console credits cannot buy the textbook's embedding, since Anthropic offers no embedding model (textbook-search-graph-in-the-panel.md). So an open embedding model on the grid makes it, which needs no key and keeps the book there, in place of Voyage, which bills through MongoDB and would send the book out before the filing (decision 6).

The template's own pages, such as README.md's "No API key anywhere.", docs/setup/claude-action.md and the start pages, describe Symphony itself, which still needs no key, and this folder's README describes how its measurements run; they stay as they are. The wording, from the owner's principle, for the Project's instructions and both CLAUDE.md files:

> Flat-rate subscriptions come first. Every feature runs entirely on flat-rate subscription accounts, and none needs an API key. Where a key is allowed, one per purpose and listed in docs/setup/keys.md with its owner and location, the subscription takes priority by default and a setting may change the order. No key is ever pasted. A key that a service can make at sign-in is made by a one-click sign-in that the owner's own app completes, and stays on the machine that uses it; a value no sign-in can make is kept as an encrypted GitHub secret, under secret scanning and push protection, and reaches that machine by the key route. No credential is ever in git, an issue, a log, a URL or browser code, and contributors' credentials are never held.

The safeguards behind it:

- Keyless first. For GitHub Actions, Anthropic's Workload Identity Federation trades the workflow's own GitHub identity token for a short-lived one, bound by a rule to one repository and branch.
- One key, seen apart. The Console sign-in adds its key to the owner's Console, where what it spends shows on its own and where it is revoked. No spend limit is set (decision 5), and the key spends only the monthly credits, as the owner set on 2026-10-25.
- Subscription first. The Console key lives only in its own sign-in folder, apart from the subscription's, and AI Scientist Pro's launcher points Claude Code at that folder only when the order setting puts the key first. Claude Code prefers ANTHROPIC_API_KEY over any sign-in whenever it is set, and then loads no connectors, so the launcher never sets it, and no workflow holds a secret of that name.
- Rotation. A fresh Console sign-in makes a new key, and the old one is disabled in the Console, at once after a suspected leak. GitHub's secret scanning and push protection are on in SchwingNet and symphony-template (read through the API on 2026-10-25), the repository's own check looks for the key's shape, and the grid readout masks long strings. Generic patterns, AI-detected secrets and validity checks are off there; the session's proxy refuses repository settings writes, so turning them on is the owner's three clicks on each repository's Advanced Security page.

The order: the owner puts the wording into the Project's instructions in place of "No API key or Claude credential anywhere."; then one pull request in each repository adds docs/setup/keys.md, and SchwingNet's docs/project.md says what "usage credits" means. The CLAUDE.md lines sit in the block cswap rewrites, so they change at the next checkpoint from a Decision: line, not by hand. The checks stay as they are. On 2026-10-25 at 21:09 UTC the owner declined to edit the Project's instructions by hand, so the project's coordinator, which can change them, applies the wording.
