It builds on native-git-locks.md (2026-10-17), whose design symphony-protocol#45 built, and on the thread "Stale branch failure statistics", which measured the cost: of 255 merged pull requests in this repository, 127 needed a catch-up merge of main and 89 went green, then stale, then ran their check again.

## 1. What the owner built, and where it stood

symphony-protocol#45, merged to the library's main on 2026-10-20 after 0.5.1 was tagged, so in no release yet. The module sdlc_protocol.locks and its git side sdlc_protocol.adapters.git_locks, behind the switch SYMPHONY_LOCKS (an environment variable, else the file .github/symphony-locks), set to off, advise or enforce, off by default. A claim claude/N takes locks on files, on single Python functions or classes and Markdown sections (path#symbol), and reads on what an edited function's code names, in one atomic push with the claim branch: the lock table LOCKS.json on the branch locks moves only by fast-forward, so git's own refusal of a non-fast-forward push is the compare-and-swap, the git-hash-based lock the owner asked for. `locks verify` then fails a pull request that edits what another live claim holds. That is both of the owner's levels, the hash lock and the dependency analysis. No repository ran it; it was kept for a coordbench arm (locks beside sdlc and serial).

Why switching it on alone would not stop the churn: a lock belongs to a claim branch claude/N, and the threads' branches are claude/project-thread-<id>, which no lock table names. The churn itself came from one GitHub rule, "Require branches to be up to date before merging" (strict required status checks), which refuses a pull request one commit behind main whether or not anything overlaps, so each merge sent every other open pull request back through a catch-up merge and a check run.

## 2. The two changes

1. The rule off. The owner ordered it off for every repository at 20:44 UTC; the Tokens and adopted repositories thread owns the ruleset source (SymphonyBoard's auto-applied settings), so SymphonyBoard stops re-applying it. Read live at 21:10 UTC on 2026-10-20: SchwingNet's ruleset 25494231 already had strict false; symphony-template's 24827932 and symphony-protocol's 24827944 still had strict true, and this session's permission check refused the PUT that would have flipped them, so that thread, or the owner by hand, flips them. With the rule off, GitHub merges a pull request onto main as main stands, git does the merge in one step, and only a real conflict stops it: the "just merge, resolve conflicts if they come" the owner asked whether Claude was already doing.

2. An overlap check for the case git merges cleanly and wrongly: main changed a function the pull request calls, or built on one it changed. `python3 -m sdlc_protocol locks overlap --base origin/main` (symphony-protocol, this thread's pull request) reads no lock table and serves any pull request, a claim's or a thread's. It takes what main changed since the branch's fork from it, as the same keys verify reads (file, symbol, <top>), with the reads an edited Python symbol's code takes (locks.plan at main's tip), and sets that beside what the branch changed with its own reads (locks.plan at the head). The branch must bring main in only where the two meet with a write on either side: main edited what the branch edits or builds on, or main built on what the branch edits. Two reads never meet. Where nothing meets, the pull request merges as it is and the required check on the merged result stays the backstop, as it is for verify. A file the library reads no symbols of (a workflow, a shell script, a binary) is whole, so two edits to one such file meet; that is stricter than git's merge, and safe. It obeys the same switch: advise prints the meetings, enforce fails on them.

## 3. What it costs and what it misses

The check runs in the pull request's own check job, one git fetch of main and a few diffs; no API call, no lock table, no server. It sees what a reference shows: a direct call, a class's methods through self, a module-level import from the repository's own modules. It does not see a dynamic call, a dependency through data or a test that only fails on the merged tree; those remain the required check's on the merged result, as they were under the rule, since the rule only reran the same check on a merged tree. So the check is not weaker than the rule on what the check can see, and it asks for a catch-up merge only where that tree could differ in meaning.

## 4. The coordbench arm

coordbench's locks arm is untouched: it vendors its own copy of the library and runs claims claude/N with locks at advise or enforce against the sdlc and serial arms, on the owner's word and number. What changes is only that the live repositories now run the switch too, so the Stale branch failure statistics thread can record a before and after: before is the 255 pull requests measured at 20:28 UTC on 2026-10-20 under the strict rule; after begins when the rule went false on each repository (SchwingNet before 21:10 UTC, the other two when the Tokens thread or the owner flips them) and, for the overlap check, when the release that carries it is vendored and the switch file lands.
