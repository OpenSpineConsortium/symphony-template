# Microsoft 365 permissions for Symphony

Source: the thread "Outlook digest with one-touch decisions", 2026-10-20, where the owner asked what delegated Microsoft Graph permissions Symphony would eventually want before the owner sends the mail request to Wayne State C&IT. It builds on docs/research/outlook-digest.md (merged 2026-10-20) and on Microsoft's own documentation read as source markdown from the microsoftgraph/microsoft-graph-docs-contrib, MicrosoftDocs/entra-docs and OfficeDev/outlook-dev-docs repositories, since learn.microsoft.com is unreachable from the cloud session.

The request to send C&IT now is small: **Mail.Send and Mail.Read, with openid, profile, User.Read and offline_access, on a second Entra app registration used only for the digest and assigned to the owner alone**, with Mail.Send alone as the stated fallback if Mail.Read is refused. Everything else on the earlier tentative list waits for the feature that uses it. The reasons are three facts from Microsoft's documentation. First, in a tenant that requires an administrator for everything, as Wayne State's evidently does, every scope is one more line for a reviewer to justify, and **Microsoft's own default consent policy now singles out Mail.Read, Calendars.\*, MailboxSettings.\*, Tasks.\* and Files.Read.All as too sensitive for a user to grant**, so each is a separate conversation with C&IT ([manage-app-consent-policies](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity/enterprise-apps/manage-app-consent-policies.md)). Second, **granting tenant-wide admin consent again "may revoke permissions that have already been granted tenant-wide for that application"**, so adding mail to SymphonyBoard Folders puts its Files.ReadWrite grant of 2026-10-19 at the mercy of the next grant's checklist ([grant-admin-consent](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity/enterprise-apps/grant-admin-consent.md)). Third, two platform limits can break the digest whatever C&IT grants: **a refresh token issued to a redirect URI registered as a single-page app expires after 24 hours, fixed**, and location-based Conditional Access can refuse Graph calls from GitHub's runners ([refresh-tokens](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity-platform/refresh-tokens.md); [CAE](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity/conditional-access/concept-continuous-access-evaluation.md)). Later phases add calendar and tasks for grant deadlines, selected SharePoint sites and OneNote for the lab, and Teams posting last; transcripts, group-wide and tenant-wide scopes stay out for a PI working under IRB constraints.

## Microsoft's default policy now treats the useful scopes as admin-only

Two separate rules decide whether a permission needs an administrator, and only the second matters in practice now. The first is Microsoft's per-scope AdminConsentRequired flag: for delegated use it is "No" for almost everything on the list, including Mail.Send, Mail.Read, Calendars.ReadWrite, Tasks.ReadWrite, Notes.ReadWrite and Files.Read.All, and "Yes" only for Group.Read.All, Group.ReadWrite.All, OnlineMeetingTranscript.Read.All, Sites.FullControl.All and the newer \*.SelectedOperations.Selected scopes ([permissions reference](https://raw.githubusercontent.com/microsoftgraph/microsoft-graph-docs-contrib/main/concepts/permissions-reference.md)). The second is the tenant's user-consent policy. **The Microsoft-managed policy, the default for a new tenant, blocks user consent to Mail.Read, Mail.ReadBasic, Mail.ReadWrite, every Calendars scope, MailboxSettings.Read and ReadWrite, Files.Read.All, Files.ReadWrite.All, Sites.Read.All, Sites.ReadWrite.All, Chat.Read, Chat.ReadWrite, OnlineMeetings.Read and, since a mid-2026 change, Tasks.Read, Tasks.ReadWrite and People.Read**; it leaves Mail.Send, Notes.\*, Files.ReadWrite and the Teams send scopes user-consentable ([manage-app-consent-policies](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity/enterprise-apps/manage-app-consent-policies.md); [MC1304287](https://mc.merill.net/message/MC1304287)). A tenant that turns user consent off altogether, which is what Wayne State's need for an administrator even for Files.ReadWrite implies (inferred; Wayne State publishes no policy), needs an administrator for every scope, User.Read included, while users keep what was already granted ([user-admin-consent-overview](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity/enterprise-apps/user-admin-consent-overview.md)).

Publisher verification does not change this. It shows a blue badge and lets a tenant allow user consent for verified publishers' apps, but only for scopes an administrator has classified as low impact, and only scopes without the admin flag can be so classified ([configure-user-consent](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity/enterprise-apps/configure-user-consent.md); [permission classifications](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity/enterprise-apps/configure-permission-classifications.md)). For Wayne State it would not remove a single admin request (inferred). It matters for the other domains below, where some tenants auto-approve low-risk scopes from verified publishers, as Illinois State says it does ([Illinois State](https://help.illinoisstate.edu/technology/support-topics/campus-applications-and-websites/microsoft-365-3rd-party-app-consent-requests), search snippet only).

How universities review such requests is public for several, though not for Wayne State, whose site returned nothing on admin consent. They route the "Approval required" prompt and its typed justification to a security team that approves, approves with restrictions, denies or asks for more; Oregon says low-risk apps typically take about a week, higher-risk ones longer ([UO KB 141226](https://service.uoregon.edu/TDClient/2030/Portal/KB/Article/141226/Admin-Consent-Requests-for-Third-Party-Microsoft-365-Apps), snippet only), and Washington keeps a page on "risky permissions" ([UW KB0034056](https://uwconnect.uw.edu/it?id=kb_article_view&sysparm_article=KB0034056), snippet only). Microsoft's guidance to reviewers is to check that the scopes match the app's purpose, its own example being a PDF viewer that asks for Mail.Read ([manage-consent-requests](https://docs.azure.cn/en-us/Entra/identity/enterprise-apps/manage-consent-requests)). The inference for the owner is that a request naming each scope, saying why the narrower one does not suffice, and offering user assignment so only the owner can sign in, is the shape that gets approved.

## Every scope Symphony could use, what it powers and how hard it is

The table below is the whole candidate list. "Default policy" is whether Microsoft's managed policy lets a user consent; at Wayne State every row needs C&IT regardless. "Review weight" is this report's judgment of how hard a university security team will look, inferred from the policy lists and the university pages above, not a Microsoft rating, since Microsoft publishes none.

| Permission (delegated) | Feature it powers | Admin flag | Default policy | Review weight (inferred) |
|---|---|---|---|---|
| openid, profile, offline_access | Sign-in; a refresh token so Actions can act without the owner present | No | User may consent | Minimal, but offline_access extends every other grant in time |
| User.Read | Read the signed-in owner's own profile; confirm the mailbox address | No | User may consent | Minimal |
| Mail.Send | Send the digest from the owner's mailbox to itself | No | User may consent | High: can send as the owner to anyone; the only Graph scope that sends mail |
| Mail.ReadBasic | See subjects and senders of replies, no bodies | No | Blocked | Moderate to high; too little for reply-to-Claude |
| Mail.Read | Read the body of a reply to the digest, to turn it into a prompt | No | Blocked | Very high: the whole mailbox, including any PHI in clinical mail |
| MailboxSettings.Read | Owner's time zone and out-of-office, to time or pause the digest | No | Blocked | Moderate; replaceable by a repository setting |
| Calendars.ReadWrite | Mirror grant and paper deadlines as events; read busy time | No | Blocked | High; there is no write-only calendar scope |
| Tasks.ReadWrite | Mirror claimed issues as To Do tasks with a link back; basic Planner plans | No | Blocked since mid-2026 | Moderate |
| Notes.ReadWrite | Index or append to the owner's own OneNote lab notebooks | No | User may consent | Moderate |
| Files.ReadWrite | Already held by SymphonyBoard Folders: own OneDrive, Word revisions, Excel workbooks | No | User may consent | Granted 2026-10-19 |
| Files.Read.All | Read files others shared with the owner, such as co-authors' drafts on SharePoint | No | Blocked | High: everything the owner can reach |
| Sites.Selected | One named SharePoint site (a lab or study site), read or write | No, but useless until a SharePoint admin grants the site | User may consent | Low once granted; needs a per-site step by an admin holding Sites.FullControl.All |
| User.ReadBasic.All | Names and addresses of colleagues, to map students to workers | No | User may consent | Low to moderate |
| ChannelMessage.Send, ChatMessage.Send | Post a status card into a lab Teams channel or chat | No | User may consent | Moderate to high; only Action.OpenUrl buttons work |
| Team.ReadBasic.All | Find the lab's team and channel by name | No | User may consent | Low |
| OnlineMeetingTranscript.Read.All | Turn lab-meeting transcripts into issues | Yes | Admin only | Very high, and a likely PHI path; also off unless an admin enables Graph transcript access |
| Group.Read.All, Files.ReadWrite.All, Sites.ReadWrite.All, Mail.ReadWrite | None that a narrower scope above does not cover | Mixed | Blocked or admin only | Not worth asking |

Four details in that table change the earlier tentative list. **Planner needs only Tasks.ReadWrite, not Group.Read.All**, so one scope covers both To Do and basic Planner plans; Premium plans are not in Graph at all ([planner-overview](https://raw.githubusercontent.com/microsoftgraph/microsoft-graph-docs-contrib/main/api-reference/v1.0/resources/planner-overview.md)). **The Excel workbook API runs under Files.ReadWrite**, which Symphony already holds, so a deviation log or data dictionary in the owner's OneDrive needs nothing new. **Microsoft Lists items need Sites.ReadWrite.All unless the narrow Selected scopes are used**, which is why Sites.Selected, with a site-by-site grant, is the version to ask for. And **MailboxSettings.Read buys only a time zone**, which a line in the repository's settings gives with no consent at all, so it leaves the list.

## The owner's own work sets the order

The owner's calendar is set by NIH and the IRB. The annual RPPR for a SNAP award is due 45 days before the next budget period starts, 60 days for non-SNAP awards ([NINDS](https://www.ninds.nih.gov/funding/manage-your-award/during-award/reporting-requirements); [U-M ORSP](https://www.orsp.umich.edu/manage-project/rpprs-u-m)); a key person's effort changing by more than 25 percent, or an absence over three months, needs prior approval ([NCI](https://www.cancer.gov/about-nci/organization/dcb/news/r15-workshop-post-award-administration)); RPPRs since 2024-10-01 must report data management and sharing, and an off-cycle change to the sharing plan goes in at least 30 days ahead ([Princeton ORPA](https://orpa.princeton.edu/news/nih-reporting-data-management-and-sharing-dms-plan-activities-research-performance-progress); [UNC RDMC](https://tdx.unc.edu/TDClient/33/Portal/KB/Article/433/RDMC-Data-Management-Guide-NIH-Guidance)). These dates live in eRA Commons and memory. Symphony can compute them as issues from the award dates and, with Calendars.ReadWrite and Tasks.ReadWrite, put them where the owner already looks, in Outlook and To Do. That is the clearest feature after the digest, which is why calendar and tasks make phase 2.

What must not move sets the limits. Wayne State's HIC policy governs any research use of PHI from medical records ([WSU IRB 10-01](https://research.wayne.edu/irb/pdf/10-01-hipaa-requirements-in-research-03-07-11.pdf)), and HHS's cloud guidance requires a business associate agreement with any service that receives PHI ([Hunton summary](https://www.hunton.com/privacy-and-cybersecurity-law-blog/hhs-releases-guidance-hipaa-cloud-computing)). GitHub and the model behind Symphony sit outside the tenant with no such agreement for this use (inferred). So the rule for every phase is that **identifiers, dates, counts and links leave the tenant, content stays**: the digest names an issue and a decision, never a subject or a scan; a reply's text becomes an issue only as the owner typed it. Mail.Read is the scope that can see clinical mail, which is why the request should say that the code reads only replies in the digest's own conversation, and why Mail.Send alone, with the card's text box carrying prompts, is a full fallback rather than a failure. Meeting transcripts stay out for the same reason, on top of the admin flag.

The owner's papers already work through Files.ReadWrite and tracked changes. Co-authors' drafts on their own SharePoint sites are the one gap; Files.Read.All would close it by reaching everything the owner can open, and Sites.Selected closes it for one named site at a time. A university will much more readily grant the second (inferred), at the cost that a SharePoint administrator must grant each site, since only an app or person holding Sites.FullControl.All can ([Selected scopes](https://raw.githubusercontent.com/microsoftgraph/microsoft-graph-docs-contrib/main/concepts/permissions-selected-overview.md)). Students are workers in the repository already, each on their own GitHub login; nothing in Graph is needed for them to work, so User.ReadBasic.All is a convenience for a later lab view, not a need.

## Other domains want the same core and differ at the edges

Across domains the low-risk, high-value pattern repeats: delegated access to one's own calendar, tasks and chosen files plus a self-sent digest of decisions, while reading others' mail or tenant-wide content is what administrators gate. An application permission such as Mail.Read reaches every mailbox in a tenant unless Exchange's RBAC for Applications scopes it, and the unscoped grant must be removed for the scope to bite ([Practical365](https://practical365.com/rbac-for-applications/)); Symphony should never ask for one. The evidence for a digest at all is general rather than academic: Microsoft's 2025 telemetry counts 117 emails and 153 Teams messages a day per worker, most email skimmed in under a minute, but excludes education tenants ([WorkLab](https://www.microsoft.com/en-us/worklab/work-trend-index/breaking-down-infinite-workday)), and a study of two million Yahoo users found people answer a smaller fraction of mail as volume rises ([Kooti et al.](https://arxiv.org/abs/1504.00704)). No study found measures decision latency itself.

| Domain | Core scopes | What differs | Main constraint |
|---|---|---|---|
| Academic labs | Mail.Send, Calendars.ReadWrite, Tasks.ReadWrite, Notes.ReadWrite | A data-sharing ledger that feeds the RPPR's sharing section; basic Planner for the lab | NIH DMS reporting; university admin consent |
| Clinical research coordinators | Mail.Send, Calendars.ReadWrite, Tasks.ReadWrite, Sites.Selected for the study site | Reminders for document expiry, deviation windows and continuing review, metadata only | PHI; Part 11 signatures and eReg stay outside Symphony ([Arizona eReg](https://healthsciences.arizona.edu/research/research-administration/ereg)) |
| Legal | Mail.Send, Calendars.ReadWrite | Deadline cross-check against the docket; partner sign-off as a decision card | Calendaring and administrative errors are 16 to 19 percent of malpractice claims ([WSBA](https://nwsidebar.wsba.org/2020/10/22/risk-management-by-the-numbers-new-aba-study-on-malpractice-claims/)); ABA Opinion 512 wants informed client consent before client data reaches a generative AI prompt ([National Law Review](https://natlawreview.com/article/american-bar-association-issues-formal-opinion-use-generative-ai-tools)) |
| Consulting | Mail.Send, Calendars.ReadWrite, Sites.Selected per client site, ChannelMessage.Send | A status card per client channel | Client NDAs and the client's own tenant |
| Software teams | Tasks.ReadWrite, ChannelMessage.Send, ChatMessage.Send | Teams cards for pull requests and decisions; To Do or Planner mirror of claims | Low; the default consent policy blocking Tasks.\* is the hurdle |
| Small business | Mail.Send, Calendars.ReadWrite, Files.ReadWrite | Bookings appointments into the digest | The owner is the admin, so consent is easy; the Bookings API covers shared bookings only and needs Business Premium ([Bookings overview](https://raw.githubusercontent.com/microsoftgraph/microsoft-graph-docs-contrib/main/api-reference/v1.0/resources/booking-api-overview.md)) |
| Teaching | Calendars.ReadWrite, Tasks.ReadWrite, Mail.Send | Course dates to tasks; counts, never student names | FERPA treats student mail as education records ([CSULB](https://www.csulb.edu/student-records/ferpa-for-faculty)), so no Mail.Read |
| Nonprofit grants | Mail.Send, Calendars.ReadWrite, Files.ReadWrite | A funder-deadline register mirrored to the calendar; board decisions by card | Grant staff report 29.5 hours a week of manual work and 89 percent at least one incident such as a missed deadline in two years ([Instrumentl](https://www.instrumentl.com/blog/beyond-shadow-work-1000-grant-professionals-on-the-work-that-matters-most-and-the-systems-holding-them-back), a vendor survey) |

The table says the phases below fit every domain, not only the owner's: Mail.Send and the calendar are universal, tasks and Teams matter most to software teams, and the domains with regulated content (clinical, legal, teaching) are the ones where Mail.Read should stay optional and off by default.

## Two design facts that the request must respect

One of the workflows notes claimed that Outlook actionable messages "now use Action.Execute and need the Bot Framework". That is wrong for Symphony. Microsoft's current pages document Action.Http as the model, with Action.Execute a separate Universal Actions path that needs card version 1.4 or later and "must be implemented as Bots", over an Outlook bot channel described as public preview; and Outlook on Mac, iOS and Android take Adaptive Cards of version 1.0 and below ([universal-action-model](https://raw.githubusercontent.com/OfficeDev/outlook-dev-docs/main/docs/actionable-messages/universal-action-model.md); [index](https://raw.githubusercontent.com/OfficeDev/outlook-dev-docs/main/docs/actionable-messages/index.md)). A self-sent card, From and To the same mailbox with no originator, renders with no provider registration ([get-started](https://raw.githubusercontent.com/OfficeDev/outlook-dev-docs/main/docs/actionable-messages/get-started.md)). So the digest needs Mail.Send and nothing from the Actionable Email Developer Dashboard. What is not documented is the token on a self-sent card's Action.Http call after the legacy token ended on 2026-06-08, since Microsoft describes the Entra token only for registered providers ([legacy token notice](https://raw.githubusercontent.com/OfficeDev/outlook-dev-docs/main/docs/includes/actionable-messages/legacy-token-deprecation.md); [Entra token setup](https://raw.githubusercontent.com/OfficeDev/outlook-dev-docs/main/docs/actionable-messages/enable-entra-token-for-actionable-messages.md)); until a live card shows it, the Worker should also carry its own limited-purpose token in the button's URL, which Microsoft's security page allows ([security-requirements](https://raw.githubusercontent.com/OfficeDev/outlook-dev-docs/main/docs/actionable-messages/security-requirements.md)).

The second fact concerns where the refresh token comes from. Microsoft says **refresh tokens sent to a redirect URI registered as spa expire after 24 hours, and tokens obtained from them keep that expiry**; every other client's refresh token lasts 90 days, sliding, and replaces itself on each use ([refresh-tokens](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity-platform/refresh-tokens.md)). If SymphonyBoard Folders' sealed token was minted through its spa redirect, Actions runs fail a day after the owner signs in, whatever the sign-in service holds. Whether the sign-in service redeems codes against a web (confidential) redirect URI, which would give the 90-day token, is not established by these notes and is the first thing to check. Either way, every run must re-seal the rotated token it receives. A separate mail app is the moment to get this right: register it with a web redirect handled by the sign-in service, so its token is the 90-day kind from the start (inferred design).

## The phased request

The case for a **separate Entra app for mail**, call it SymphonyBoard Mail, rests on Microsoft's warning that a new tenant-wide grant may revoke earlier ones for the same app ([grant-admin-consent](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity/enterprise-apps/grant-admin-consent.md)): with two apps, C&IT reviews mail on its own, a refusal or later revocation cannot touch Folders, and the mail app can require user assignment with only the owner assigned, which Microsoft says forces admin consent anyway and confines who can sign in ([configure-user-consent](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity/enterprise-apps/configure-user-consent.md)). The cost is a second sign-in and a second sealed secret. If the owner prefers one app, the request should list Files.ReadWrite and offline_access again beside the new scopes, and the owner should confirm on the Folders tab afterwards that files still work. Static registration matters too: Microsoft's admin consent screens know only the permissions listed on the registration, so each phase's scopes are added to the registration before the request ([consent-types-developer](https://raw.githubusercontent.com/MicrosoftDocs/entra-docs/main/docs/identity-platform/consent-types-developer.md)).

### Phase 1, to ask C&IT for now: the digest

| Permission | One-line justification for C&IT |
|---|---|
| openid, profile | Sign the owner in to the digest app; no data beyond name and sign-in. |
| User.Read | Read the owner's own profile to confirm the mailbox the digest goes to and from. |
| offline_access | Let the scheduled digest run without the owner signing in each day; the token is sealed in a GitHub secret and can be revoked by C&IT at any time. |
| Mail.Send | Send one digest a day from the owner's mailbox to the same mailbox only; the code has no other recipient. |
| Mail.Read | Read only the owner's replies in the digest's own conversation, to file them as tasks; requested separately so it can be refused alone, in which case the digest's buttons and text box carry the answers instead. |

Ask for it on the separate app, assigned to the owner only, delegated only, with the statement that no application permission is requested and no PHI leaves the tenant. Mail.ReadBasic is not offered as a middle step because it excludes the body, which is the whole of a reply.

### Later phases, each tied to a feature

| Phase | Trigger feature | Permissions | What it takes |
|---|---|---|---|
| 2 | Grant and paper deadlines computed from award dates, mirrored to Outlook and To Do | Calendars.ReadWrite, Tasks.ReadWrite | A second C&IT request; both are blocked by Microsoft's default policy, so a reviewer will look; on the Folders app or a third "planner" app |
| 3 | Lab collaboration: co-authors' SharePoint drafts, the lab's OneNote notebook | Sites.Selected (per site), Notes.ReadWrite | C&IT consent plus a SharePoint administrator's grant for each named site; Notes.ReadWrite covers only the owner's own notebooks |
| 3, if Sites.Selected is refused | Same, wider | Files.Read.All | Expect more scrutiny; reaches everything the owner can open |
| 4 | Status cards into a lab Teams channel or chat, link buttons only | ChannelMessage.Send, ChatMessage.Send, Team.ReadBasic.All | C&IT consent; one-press buttons in Teams would need a bot, which conflicts with having no server of Symphony's |
| Optional | A lab directory view | User.ReadBasic.All | Low; ask only when a feature needs names |
| Not requested | Transcripts, group content, write-all or read-all mail and sites, any application permission | OnlineMeetingTranscript.Read.All, Group.\*, Mail.ReadWrite, Files.ReadWrite.All, Sites.ReadWrite.All, MailboxSettings.\* | The narrower scopes above cover each use; transcripts are an admin-flagged PHI path |

### Risks and open questions to test before relying on the digest

Seven things should be tested, roughly in this order, because each can make an approved permission useless. First, whether Folders' sealed refresh token comes from a spa or a web redirect, by checking its age after 25 hours; if spa, the mail app must use a web redirect. Second, whether Wayne State applies location-based Conditional Access or a sign-in frequency policy to Graph, which would refuse or cut off calls from GitHub's runners; the test is one Actions run that calls /me/drive with the sealed Folders token, and the answer may push the sending step onto the WSU grid's runner or the owner's own machine (inferred). Third, whether Wayne State's Exchange has actionable messages turned off with Set-OrganizationConfig, which only C&IT can say and which a self-sent test card would reveal ([get-started](https://raw.githubusercontent.com/OfficeDev/outlook-dev-docs/main/docs/actionable-messages/get-started.md)). Fourth, what token a self-sent card's button carries since 2026-06-08, measured on the first live card. Fifth, whether the card's buttons work in Outlook for iOS, where late-2025 community reports say they sometimes do nothing, and in the new Outlook for Windows, which Microsoft's client table does not name. Sixth, whether C&IT's grant on a separate app leaves Folders' grant untouched, checked by listing both apps' grants after approval. Seventh, Outlook's limit of four concurrent requests per app per mailbox, which the sign-in service, the Worker and Actions together can hit if they act at once ([Outlook throttling](https://raw.githubusercontent.com/microsoftgraph/microsoft-graph-docs-contrib/main/includes/throttling-outlook.md)).

Two questions only C&IT can answer belong in the phase 1 request itself: which consent policy Wayne State runs, so later phases can be shaped to it, and whether its SharePoint administrators perform per-site Sites.Selected grants on request, which decides whether phase 3 is narrow or broad.

## Conclusion

The useful shift is from a list of scopes to a list of conversations. Microsoft's mid-2026 policy changes mean that, even in a tenant with user consent on, nearly every scope worth having beyond sending mail is now an administrator's decision, so each phase is a separate review that should arrive with its feature already built and demonstrable. Asking for less now makes the first approval faster and keeps a refusal of Mail.Read from costing anything, since Mail.Send alone already delivers the one-press digest.

The larger risk is not consent but plumbing that consent cannot fix: a 24-hour token, a location policy that refuses GitHub's runners, or an organization switch that hides cards. The first two take one test with the Files permission Symphony already holds, and the card tests need only a self-sent card from the Actionable Messages designer, so all of them can run before or alongside the request to C&IT, and the request can ask for exactly what will work.
