# Outside code bases: what Symphony would take from each, and how

Written 2026-10-16 for the owner's ask of 2026-10-16 00:20 UTC: start thinking about integrating four code bases, and anything relevant in the attached PDF, either as libraries or by extracting code, into Symphony's code base or as another repository, to increase Symphony's power. The four are Decentralized-LM/delm-agent-plugin, SkeinRank/claim-plane, FSoft-AI4Code/HyperAgent and Roman-Simone/autonomous-software-agent. The PDF is the deep-research note of 2026-10-15 on native git plus DeLM, which OpenSpineConsortium/coordbench already holds as bench/cooperbench/results/curse-of-coordination-notes/research-git-delm.md; the candidates it adds are DeLM's research harness, git-test, grite, Git AI, Bazel's action cache and the CALM theorem.

This page is an assessment, not integration code: the owner said "start thinking", so nothing is built until the owner chooses from it. Every repository was cloned and read at the commit section 6 names, and a size is a count of lines in that clone. The yardstick is Symphony's own rules: Python 3.12 and its standard library, plain bash and GitHub's own actions, and no new dependency without an issue first (.claude/rules/writing.md); no API key and no stored Claude credential anywhere; the protocol's rules change in OpenSpineConsortium/symphony-protocol and nowhere else (docs/memory/protocol-changes-come-from-symphony-protocol.md); and a change that spends tokens is measured in coordbench before it is adopted, which is the rule the research folder sets for itself. An estimate of effort is marked as inference.

## 1. The short answer

None of the four is taken as a library, and no code is copied from any of them. What they offer Symphony is three ideas and one measurement:

- Check receipts, from delm-agent-plugin: a command's outcome bound to the exact files it depended on, reusable by a peer while those files are unchanged. Symphony has the required check per pull request head and nothing finer.
- Pre-write scope admission, from Claim Plane: a worker declares the files and symbols it will touch, a model-free control plane admits, orders, serializes or denies the work before it starts, and the actual diff is checked against what was granted. Symphony claims at issue granularity, tells overlaps on the board and orders them at landing, and enforces only at the merge; nothing refuses work before it is written, by design, since that needs a server.
- Same-task parallelism, from DeLM: two agents on one task, sharing findings and dividing checks, finished sooner and more often than one agent on DeLM's benchmarks. Symphony's unit is one issue, one branch, one pull request, and it says nothing about how a worker works inside its claim.
- A head-to-head on the same benchmark, from Claim Plane: it is the only published competitor measured on CooperBench, which is what coordbench runs Symphony's arm on.

## 2. What Symphony is, for this comparison

Symphony keeps every coordination state in GitHub objects and reads it by code: an issue is the unit of work, the first push of `claude/<issue>` is the claim, the draft pull request is the work in the open, the board on the branch `board` lists who holds what and which open work meets in a file, the coordinator releases idle claims and tells overlaps in the board's own run, and the required check on the pull request's head is the only gate (docs/agents/PROTOCOL.md). The rules live once, in OpenSpineConsortium/symphony-protocol: 7,079 lines of Python with no dependencies and 22,025 lines of tests, vendored into four consumers, released by the owner's approval only; 0.4.1 is the only release and the fixes toward 0.5.0 are on its main. The protocol check (sdlc_protocol.protocol_check) holds a claim pull request to the claim file, the "Closes" line, the repository and the branch's name, and does not compare the pull request's files with its claim's list: the board takes the pull request's own files once it has any and tells the worker whose work it meets.

The taxonomy review of 2026-10-15 sorted the tools around Symphony into three groups (docs/checkpoints/2026-10-15b/taxonomy/research/notes/03-coordination-evidence.txt, "Relation to Symphony overall"): claim and admission layers that overlap Symphony's claim protocol, Claim Plane among them; shared-memory layers Symphony lacks and could add as git notes keyed to content, DeLM's receipts among them; and read-less retrieval tools orthogonal to coordination. This page follows that sorting: group one is measured against Symphony, group two is the one thing worth adding, and group three belongs to the beyond-cooperation programme.

What a worker's session runs inside its claim is not the protocol's business. A person on a Mac may run delm-agent-plugin inside a claim branch today, and the result still lands by the pull request and the check; nothing in Symphony has to change for that, and nothing in Symphony can measure it either, which is why the arm comes first.

## 3. The candidates

### 3.1 delm-agent-plugin (Decentralized-LM, MIT, commit 3bd42f9 of 2026-10-07)

What it does. A plugin for Claude Code and Codex, installed with `npx --yes delm-agent@latest install` on macOS 13 or later with Node 22 or later; Claude Code must be 2.1.289 or later (README.md, "Install on macOS"). On `/delm:run <task>` the plugin's module captures the project into a copy-on-write snapshot, prepares two private working directories, and has the parent conversation issue exactly two native Agent calls with `subagent_type: "fork"`, so both workers inherit the whole conversation (hosts/claude/skills/run/SKILL.md; docs/architecture.md, "Claude Code"). The workers coordinate through a board of tasks, contributions and check receipts served by a Rust sidecar over MCP; every board call needs a one-use ticket the module mints, bound to the worker, the turn, the tool and its exact arguments, so the MCP server cannot be used on its own (docs/architecture.md, "Claude Code"). Delivery applies the accepted source into the original project, keeps the user's index, merges compatible concurrent edits and reports conflicts without overwriting them (docs/architecture.md, "Delivery, recovery, and shutdown"). The copy-on-write step has no fallback, so the installer refuses any platform but darwin (docs/support.md line 13; packages/installer/lib/installer.mjs lines 32 to 34). The source is 49 Rust files, 33,161 lines with its tests; the Claude host adds about 300 KB of JavaScript hooks; the repository also carries an 84 MB video demo.

The two ideas worth having. First, the check receipt (src/board/checks.rs, 599 lines: `begin_check` at line 68, `finish_check` at 118, `shared_checks` at 268). A worker calls `delm_check_begin` with an explicit scope of input files, each recorded as sha256, byte count and executable bit, with absence recorded too; runs the command; calls `delm_check_finish` with the snapshot id and the native command's id; the runtime re-hashes the scope and marks the receipt reusable only when the inputs are unchanged and the command passed. A peer may cite the receipt instead of re-running the command when its own files equal the recorded versions, and `shared_checks` refuses a receipt whose scope differs from the current files. The plugin states the limit itself: a receipt "establishes the observed outcome for those recorded inputs; it does not prove coverage, undeclared dependencies, ambient environment state, or the absence of transient changes between observations" (docs/architecture.md, "Verification and previews"). Second, the version-fenced claim: every task has a version, and an update, release, split or finish must carry the version the worker last saw, so a stale owner cannot finish reassigned work, and either worker may hold the one integration claim (docs/architecture.md, "Workspaces and coordination"). The worker policy, plugin/worker.md, is 17 paragraphs of prose any worker prompt could learn from: claim before substantial work, publish partial files early, keep independent work visible rather than one broad claim, never sleep for a peer, declare waiting with a named dependency and end the turn.

What Symphony would gain. A receipt is the one shared-memory object the taxonomy review found Symphony lacks: today a worker that has run `bash scripts/check.sh` has nothing to show a peer but the check run on its pull request's head, and a peer with the same files unchanged runs the same check again. On GitHub the saving is bounded, because the required check re-runs on every push whatever anyone recorded; the saving is in sessions, which decide whether to run the tests locally before pushing, and in coordbench's pairs, which have no CI at all. The version-fenced claim is already Symphony's: the claim is exclusive by the first push, and the release and the re-claim are the coordinator's; what DeLM adds is the split, which Symphony's planning step does for epics only.

Library or extraction. Neither. The plugin is a Rust binary for macOS that runs two forks inside one Claude Code process, and Symphony's workers run in separate clones, containers and accounts. The ideas are small enough to re-implement: coordbench's git-delm-design.md, section 3, specifies the hub tools (`board-claim` with a version, `board-release`, `board-split`, `fact-add` keyed by blob ids, `certify` keyed by the tree id) and estimates them at 300 to 400 lines of Python plus tests against DeLM's 684. In Symphony proper the natural form is a commit trailer beside Symphony-Usage, such as a Symphony-Check line naming the command, its exit code and the tree of its scope, since trailers travel with the branch, show on github.com and fall under the rulesets, where notes refs do none of those (inference from GitHub's rulesets, which target branches and tags).

Where, effort and risk. coordbench first, as step 2 of the order, with the experiment's own measurement fixes before it (git-delm-design.md, section 4, tier A). The protocol change after that, through the protocol thread and after 0.5.0, as its own finding entry in the validation harness. The risks are in the table: the plugin changed within the last two weeks and runs two agents only; a receipt without the command and an environment digest in its key is weaker than it looks (the PDF's findings 2 and 3); and the saving may be invisible on the session route, where each board call re-reads a prompt of about 80,000 tokens, which the design note says to fix before any run.

### 3.2 DeLM, the research harness (yuzhenmao/DeLM, MIT, commit 6661761 of 2026-10-08)

What it does. The Stanford harness behind the paper (arXiv 2606.10662): n equals 2 or 4 agents, each in its own container from the task's image, each a plain `claude -p` or Codex session driven through Humanize, reaching a shared board only as a shell command (board/context.sh). The board is an append-only event log in SQLite served by an HTTP server (board/shared_context.py, 639 lines, with board/protected_board.py, 45 lines): `claim` is a compare-and-swap on an open item with at most one unfinished claim per agent, `reserve` creates and claims, `done` closes, `note` records a FACT or a FAIL with a scope and a basis, `publish` shares whole files, and `apply` refuses the whole batch when any file conflicts, leaving reconciliation to the agent (protected_board.py line 11; README.md, "the engine does not automatically merge conflicting edits"). There is no release, no expiry and no split. On Terminal-Bench 4.0 with Claude Opus 5.5 it reports 81.67% in 130.75 minutes for Claude Code alone against 93.33% in 64.77 minutes for two agents, and on DeepSWE 71.67% against 88.33% (README.md, "Results"), each agent graded alone on the whole task.

What Symphony would gain, and why not as code. The lever is two agents on one whole task sharing what they find, which is a different setting from CooperBench's two features on one base and from Symphony's one issue per worker; the gain in Symphony's setting is unmeasured, and the design note says so (git-delm-design.md, section 1.3). The harness cannot run under Symphony's rules as it stands: its subscription mode reads a `claude setup-token` token from a mode-600 file mounted into each container (README.md, "Claude Code with a coding plan"), it owns Docker and refuses to start while any container runs, and it reads Terminal-Bench tasks only. Its board could be vendored, 684 lines of standard-library Python under MIT, but its file transport and whole-file apply would be replaced by git fetch and merge in any case, so porting the semantics is simpler than carrying the code (the design note's inference, which this page agrees with). The ideas it adds beyond the plugin's are the per-agent incremental read with a long-poll wait, and FACT and FAIL notes with a scope; both are in the arm's design.

### 3.3 Claim Plane (SkeinRank, Apache-2.0, 0.56.3 at commit 82676e5 of 2026-09-17)

What it does. "Deterministic execution control for concurrent coding agents": before a worker writes, it declares a ChangeIntent of files and, for Python, symbols and regions; the control plane admits the work as parallel, ordered, serialized or denied against the live repository, with no model call; scope growth is re-admitted as an amendment; workers run in isolated git worktrees; one integration consumer lands work serially while others run; after execution the actual staged diff is re-derived and checked against the granted authority; every decision is a durable evidence record (README.md, "How it works"; docs/GUARANTEES.md). Its confirmatory study on CooperBench, 30 frozen pairs, three coder seeds and four arms, raised pair pass from 23.3% unconstrained to 50.0% under static admission, a gain of 26.7 points with a bootstrap interval of 9.6 to 60.0, and on conflict-labelled pairs from 6.7% to 60.0%; static admission serialized 96.7% of executions, dynamic admission reached 22.2%, and the README says the result "establishes a reliability result, not a wall-clock speedup claim" (README.md, "Results"). The planner that wrote the intents ran once through OpenRouter under an oracle-localized context, and the published study's arms are frozen in experiments/cooperbench/ (its README).

The code. 70,770 lines of Python in src/claim_plane (the swarm runtime alone is 18,108, code intelligence 3,590, integration 3,778) and 27,047 lines of tests in 86 files; `dependencies = []` in pyproject.toml, with optional extras for SCIP and signing; Python 3.10 or later. The only agent adapter is Codex (src/claim_plane/connectors: codex.py, codex_adapter.py, codex_guard.py and their kin; the word "claude" occurs nowhere in src or docs); the swarm runner starts `codex` as a subprocess (src/claim_plane/swarm/codex_runner.py line 621). The state store is SQLite with WAL and leases on one host; two machines need "a single network-authoritative registry" the project describes as the commercial control plane (docs/STORAGE_BACKENDS.md). The MCP server, `claim-plane-mcp --db .claim-plane/plane.db`, serves about two dozen tools, among them admit_change_intent, amend_change_intent, heartbeat_intent, complete_intent, release_intent, verify_change_manifest, run_integration and claim_artifact (src/claim_plane/mcp/server.py from line 50), and that server is how a Claude Code agent would use it, since Claude Code loads MCP servers and needs no adapter. Its acceptance discovery prefers an existing scripts/check.sh (docs/INTEGRATIONS.md), which is Symphony's check by name. The taxonomy review's uniqueness table reads it the same way: no shared state across hosts, leases in SQLite, no GitHub, no forge (docs/checkpoints/2026-10-15b/taxonomy/research/verify/03-uniqueness.txt, line 45).

What Symphony would gain. The measurement first. Claim Plane and Symphony answer the same question at different points: Claim Plane refuses or orders work before it is written, on one host, through a database; Symphony tells overlaps on the board, orders them at landing, and refuses only at the merge, through GitHub, with no server. Claim Plane's published number says serialization, not parallelism, bought its pass rate; Symphony's step of eight pairs found no curse to cure and sdlc the slowest arm, with about a third of its agent time waiting (docs/checkpoints/2026-10-15b/handoff.md, section 2.3). An arm that runs Claim Plane's admission beside sdlc on the same pairs, same model and same effort is the one experiment that puts both claims on one scale, and it is the figure a reviewer of the grant or the taxonomy would ask for. Second, and only if that arm shows it, a serialize-before-start option: a worker whose claim lists a file another open claim lists waits until the first lands, which is the board's Overlaps order applied at the start of work rather than at its end; the protocol's telling half already exists and re-tells when new overlaps start (docs/agents/PROTOCOL.md, "Overlaps").

Library or extraction. Neither into Symphony. As a library it is 70,000 lines with a Codex-only adapter and a single-host store, under a rule that admits no dependency without an issue; as an extraction, its admission logic depends on its registry, its worktree allocation and its code intelligence together, and the one rule Symphony might want is a sentence in the spec, not a port. Beside Symphony, as a benchmark arm, it is cheap: an arm directory on the pattern coordbench's README gives ("An arm is a Claude Code plugin"), the MCP server in each task container, a prompt section that has the agent declare an intent before its first write and amend it when the scope grows, and a count of admissions, amendments, denials and serialized waits in the arm's metrics. The off-the-shelf survey of 2026-10-15 named this arm as the one maintained third-party tool to try and gave its constraints: python3 is not guaranteed in the task images, the session route drops MCP servers, so the arm runs on the claude-cli route only, and its HMAC-signed observation tools need a local secret and stay unused (coordbench's off-the-shelf.md, section B).

Where, effort and risk. coordbench, as step 3 of the order, after the full run. About two days for the arm and its smoke check (inference), plus the runs the owner chooses, on bench.yml's real mode in Actions or on the owner's machine with git 2.38 or later. The risks: the serialization that produced its gain is wall time the benchmark must report; a technical preview at 0.56.3 whose "APIs and evidence formats may change before 1.0"; the PyPI release the survey saw was 0.37.31, so the arm installs from the repository at a pinned commit.

### 3.4 HyperAgent (FSoft-AI4Code, commit c3092f2 of 2024-11-07)

What it does. A generalist software-engineering agent from FPT Software: a Planner, a Navigator, a Code Editor and an Executor, each an LLM call through OpenAI, Azure, Groq, vLLM or a local model (src/hyperagent/agents/llms.py), with Anthropic's API named by key in the README's example configuration; code search through Zoekt and universal-ctags, language servers through multilspy, parsers through tree-sitter and LangChain; a conda environment named hyperagent with a Jupyter kernel for the Executor; task runners for SWE-bench, RepoExec and Defects4J under scripts/; a VS Code extension under hyperagent-ext. It reports 31.4% on SWE-bench Verified and 25% on SWE-bench Lite, 53.3% pass at 5 on RepoExec and 249 Defects4J bugs fixed (README.md, "Overview"). 15,023 lines of Python, a requirements.txt of several hundred pinned packages, no commit since 2024-11-07. The LICENSE file is Apache-2.0 while the README badge, the README's licence line and the classifier in pyproject.toml say MIT; anyone copying from it would have to ask which the authors mean.

What Symphony would gain. Nothing as code. Symphony's agent is Claude Code, which plans, navigates, edits and runs in one harness with its own tools, on a subscription, with no key; HyperAgent is a 2024 answer to the same need on API keys, with a dependency list Symphony's rules forbid several times over, and it is dormant. Two of its parts are questions other programmes already hold: the Navigator (Zoekt plus a language server, so the agent reads spans rather than files) is the "decreased code reading through hashing and retrieval" row of docs/research/beyond-cooperation on the branch of symphony-template#94, whose arms are measured before any is adopted; and its SWE-bench and Defects4J runners are examples for the agentic-workflow-benchmarks thread, which compares coordbench-like harnesses. Each of those pages may cite it; neither should take from it.

### 3.5 autonomous-software-agent (Roman-Simone, commit 80b5d64 of 2024-10-07)

What it does. The project of a master's course on autonomous software agents at the University of Trento: a belief-desire-intention agent that picks up and delivers parcels in the Deliveroo.js game, in JavaScript (2,240 lines under ASAP/) with a PDDL domain solved through a planning service; `node index.js ONE agent_1` runs one agent, `node index.js TWO agent_1` and `agent_2` run two, which find each other by a handshake over the game's socket and take the roles MASTER and SLAVE (ASAP/communication/coordination.js). There is no LICENSE file; package.json says ISC. There is no .github folder, so the Actions tab the owner linked holds no workflow.

What Symphony would gain. Nothing. It is neither a software-engineering agent nor a coordination layer for one; the belief-desire-intention loop it illustrates, beliefs updated from the world, options scored, one intention pursued and revised, is a textbook architecture that Symphony's workers already follow in their own terms, with the issue as the desire, the claim as the intention and the board as the belief. If the owner meant another repository by this link, this page takes the correction.

### 3.6 The rest of the PDF: git-test, grite, Git AI, Bazel's action cache and CALM

The PDF's thirteen findings were verified by three votes each on 2026-10-15 and are not re-verified here; this section says only what each of its candidates is to Symphony.

- git-test (mhagger/git-test, GPL-2.0, commit 31b340b of 2025-03-13; bin/git-test, 1,320 lines of Python) records a test's result as a note under refs/notes/tests/<name> keyed by the commit's tree, so a result survives rewording, squashing and tree-preserving rebases (README.md). The key is what the arm's `certify` takes (git-delm-design.md, section 3.3); the code is not, since GPL-2.0 code cannot go into MIT code, and the PDF's own caveat stands: keyed by test name and tree, not by command, so a changed command keeps stale results.
- grite (neul-labs/grite, MIT, 0.5.3 at commit 33afee0 of 2026-07-02; 23,505 lines of Rust in seven crates, with wrappers on npm, PyPI and RubyGems) keeps an issue tracker as an append-only event log in refs/grite/wal, merged as a CRDT, with lease locks in refs/grite/locks/<hash> whose policy is off, warn or require (docs/locking.md), all synced by plain fetch and push, and an optional daemon. It is the precedent that a project's coordination state can live in refs of its own and travel with the code. Symphony keeps its queue in GitHub Issues on purpose, where people and workflows read it for free, and its locks are the first push of a branch, which GitHub itself refuses a second time; a lock in a ref is advisory unless a server-side hook enforces it, and the PDF's finding 8 and the design note's section 2.2 showed how easily a ref claim is taken. Nothing to take; its namespace discipline (refs/grite/*, never the working tree) is what a Symphony notes ref would copy.
- Git AI's standard keeps agent authorship notes in refs/notes/ai, never in refs/notes/commits, and syncs them by fetch, merge with ours and a fast-forward push retried on refusal (the PDF's findings 8 and 9). Precedent for the namespace and the loop; for results that only grow, a union merge (cat_sort_uniq) and one ref per writer fit better, as the PDF's finding 10 says.
- Bazel's action cache keys a result on a hash of the action's declared inputs, output names, command line and environment, and keeps outputs in a content-addressable store (the PDF's finding 2). That is the shape of a receipt key that proves more than a blob's note does: the tree of the scope, plus the command, plus an environment digest.
- CALM (the PDF's finding 10): a program has a coordination-free consistent implementation exactly when it is monotonic. Adding receipts to a store that only grows and is merged as a union needs no lock; claiming, releasing or declaring a result final needs a compare-and-swap. Symphony already has the second as the first push; the first is what a receipt store would be.
