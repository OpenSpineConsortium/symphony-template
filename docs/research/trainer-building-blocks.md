# A model trainer made of swappable building blocks, under a reproducible record

Source: the project thread "Improve SchwingNet training and review end-to-end status", 2026-10-24. The review itself, its findings about one model and the state of that project's workflow are confidential and live in OpenSpineConsortium/SchwingNet (docs/research/training-review.md, docs/memory/training-blocks.md, pull requests #200, #201 and #202 there); this note keeps only what any Symphony project that trains a model can reuse.

## What generalises

- **Each part of training is a named block, and naming none reproduces the old run to the bit.** Normalisation, augmentation, optimiser, schedule, sampler, loss weights and the checkpoint metric each get a tuple of allowed names in a pure module under the contracts gate, and a table of one function per name on the torch side. A run picks with `--block KEY=VALUE`; the defaults are exactly the previous trainer, proved by a test that trains one epoch through the new path and through a copy of the old loop and compares every weight. A better way of doing one part is one name and one function, so the owner can swap a method without touching the trainer or voiding earlier records.
- **Record the blocks with the checkpoint and rebuild the model from them.** Every tool that loads the checkpoint (evaluation, latency, ONNX export, decoders) builds the model from the checkpoint's own record, so a run's preprocessing cannot drift between training and use. Input scaling done as a forward pre-hook, not a new layer, keeps the weights' names unchanged, loads old checkpoints as they were, and is carried by the ONNX export (parity tested).
- **A deterministic flag that only warns does not make a GPU run repeatable.** `torch.use_deterministic_algorithms(True, warn_only=True)` lets cuBLAS stay nondeterministic unless `CUBLAS_WORKSPACE_CONFIG` is set before CUDA starts; a record that promises "same commit, data and seed give the same run" needs the variable set in the seeding function, before the model reaches the device.
- **Decode a frame once for all its crops.** A loader that crops several objects per image and decodes the image per object does the work several times; keeping only the last decoded image keeps the output identical and the memory flat.
- **The search space is the block list.** Automated tuning frameworks (for example MedicalMLOmni, arXiv 2610.28410, read from its abstract) search architectures and hyperparameters with parallel agents; with blocks, a sweep is a plan of runs over block choices, scored on validation frames only, and in a project whose rule is no run without the owner's word, the planner prints the plan and its job count and starts nothing.
