# A model trainer made of swappable building blocks, under a reproducible record

Source: the project thread "Improve SchwingNet training and review end-to-end status", 2026-10-24. The review itself, its findings about one model and the state of that project's workflow are confidential and live in OpenSpineConsortium/SchwingNet (docs/research/training-review.md, docs/memory/training-blocks.md, pull requests #200, #201 and #202 there); this note keeps only what any Symphony project that trains a model can reuse.

## What generalises

- **Each part of training is a named block, and naming none reproduces the old run to the bit.** Normalisation, augmentation, optimiser, schedule, sampler, loss weights and the checkpoint metric each get a tuple of allowed names in a pure module under the contracts gate, and a table of one function per name on the torch side. A run picks with `--block KEY=VALUE`; the defaults are exactly the previous trainer, proved by a test that trains one epoch through the new path and through a copy of the old loop and compares every weight. A better way of doing one part is one name and one function, so the owner can swap a method without touching the trainer or voiding earlier records.
- **Record the blocks with the checkpoint and rebuild the model from them.** Every tool that loads the checkpoint (evaluation, latency, ONNX export, decoders) builds the model from the checkpoint's own record, so a run's preprocessing cannot drift between training and use. Input scaling done as a forward pre-hook, not a new layer, keeps the weights' names unchanged, loads old checkpoints as they were, and is carried by the ONNX export (parity tested).
- **A deterministic flag that only warns does not make a GPU run repeatable.** `torch.use_deterministic_algorithms(True, warn_only=True)` lets cuBLAS stay nondeterministic unless `CUBLAS_WORKSPACE_CONFIG` is set before CUDA starts; a record that promises "same commit, data and seed give the same run" needs the variable set in the seeding function, before the model reaches the device.
- **Decode a frame once for all its crops.** A loader that crops several objects per image and decodes the image per object does the work several times; keeping only the last decoded image keeps the output identical and the memory flat.
- **The search space is the block list.** Automated tuning frameworks (for example MedicalMLOmni, arXiv 2610.28410, read from its abstract) search architectures and hyperparameters with parallel agents; with blocks, a sweep is a plan of runs over block choices, scored on validation frames only, and in a project whose rule is no run without the owner's word, the planner prints the plan and its job count and starts nothing.

## The loop around the blocks (the thread "Build plug-and-play training experiment framework", 2026-10-24)

The owner's follow-up ask was something to build on "to continually optimize both which samples i use, which architectures, which denoising, augmentation, ect as plug and play pieces". What was added in SchwingNet (its #207) and what of it generalises:

- **Four commands make the loop, and the record is what the loop reads.** `parts` prints every plug-in point from the code (the part, its names, the default), so the list cannot go stale; `plan` prints the run commands, the run count and the GPU-hours of every combination and starts nothing; the runs write their blocks, their parent and the counts of samples seen and offered into the checkpoint's record; `ledger` finds every run under a folder by its record and tables the blocks that differ from the default beside the validation numbers and the latency headline. The next plan is made from the ledger. Choosing from validation only, with the test part read once for the chosen run, is the rule that keeps a sweep honest, and the ledger enforces it by never reading the test results.
- **Sample selection is a block too, and it never touches the validation part.** Which training samples a run sees (only or except named sources, or the first N per person in the data's fixed order) is a named choice recorded with the run; the validation part stays whole so every run of a comparison scores the same samples. A deterministic cap (the first N in the catalog's own order) beats a seeded random one: it is reproducible without a seed and changes one thing at a time.
- **A preprocessing step the model needs at inference belongs inside the model.** A denoising filter registered as a forward pre-hook, before the input scaling, is carried by every reader and by the ONNX export; the export carries a median filter when it is written as nine shifted slices and a sort rather than an unfold or a median op. A kernel built from the input's shape is "of unknown shape" to the TorchScript exporter; a kernel built from plain numbers is a constant.
- **A new backbone is one table entry, with its head named.** The one thing that differs between torchvision's classification networks is the name of the layer the task replaces; a table of head prefixes per architecture lets one loader drop the ImageNet head, refuse a file of a sibling network (its names fit and its shapes do not, which load_state_dict raises rather than reports) and give the backbone a smaller learning rate than the new head.
- **MedicalMLOmni, read in full.** Shen and Unberath (arXiv 2610.28410, 20 October 2026) is not a package but an LLM agent (Qwen3-30B) that retrieves configurations from a frozen PubMed and arXiv snapshot, writes and retries the training code in a sandbox, and refines with parallel HPO agents that each own one category (architecture, augmentation, regularisation, schedule) before aggregation; its implementation layers are MONAI, LLaMA-Factory and AutoGluon-Multimodal, its benchmarks 3D segmentation, VQA and multimodal fusion, and it gives no code link. For a project whose numbers must come from a commit and a seed, the generated-code loop is the wrong shape and its packages are a dependency decision, not a drop-in; what carries over is that its HPO categories are the blocks, so a planner that reads the ledger and proposes the next plan on one block at a time, run only on the owner's word, is the same structure without the code generation. Its own ablation attributes about half its gain to planning and retrieval and half to the parallel HPO (Dice 0.883 to 0.910 over eight segmentation benchmarks).

## What an adversarial review of the loop added (the same thread, later on 2026-10-24)

Five reviewers read the change through one lens each and two refuters judged every finding; fourteen findings, all reproduced, four in the code's behaviour and ten in what the record and the notes said of it, and what they teach any project that builds such a loop:

- **A sweep's starting weights are per architecture.** One ImageNet file is one network's; a planner that copies the one file into every command of a sweep over architecture plans a run that can only die after the job has loaded its data. The planner takes a file per architecture named, and refuses a sweep in which one run would start from pretrained weights and another from nothing, since its rows would compare the start and not the block.
- **The record keeps a block's cut apart from a dry run's cap.** When a tool both selects samples by a named block and caps them for a quick run, counting only the final number credits the block with the cap, and the ledger read for the next plan cannot tell the two apart; the record keeps the count after the block and the count after the cap, and the words say which cut which. The same for a validation part a cap shortened: the record says how much of the part was read, never "whole" by default.
- **A name the data does not hold is refused where the data is in hand.** A pure selection function cannot know the catalog, so a misspelled source name silently selects nothing, and the record then shows a cut that was never made; the check belongs at the one place that holds both the names and the rows, and a list parsed from a pasted command strips its parts, since a space is never part of a name.
- **A ledger over a folder names the run it cannot read.** A walk over many runs meets a half-written or foreign record sooner or later; an exception that prints as nothing (StopIteration) loses the whole table and names no run, so each run's read is wrapped to name the folder and what it lacks, links are followed since a runs folder may link to a volume, and a run named "." is resolved before its name is printed.
- **A reproducibility claim names its device.** torchvision's networks with Dropout or StochasticDepth (mobilenet-v3-small, efficientnet-b0) draw from the device's global generator, not from the run's CPU generator the blocks draw from; the refuters held that no promise broke, since CPU and CUDA kernels diverge for every network anyway and the project promises same-machine reproduction, but a docstring that said "whatever the device" was wrong in letter and now says on what device a run reproduces.
- **A number in a note is counted, not recalled, and a recipe in a note is run.** The note called the small backbone "about a tenth" of the large one's multiply-adds; counted with forward hooks it is about a thirtieth, and torchvision publishes the figures. The note's recipe for adding a piece ("two lines") left out the entry a part keys by name and the entry a new part needs for the parts list to print it, which a reviewer found by following the recipe and watching the test fail. The sentence "never reads evaluate/" was false by one file, the latency headline that lives there. Ten of the fourteen findings were of this kind: the code was right and the words about it were not, which is where a record-first project is most exposed.
