# How a service states a file's size before download

Source: the thread "Add fetch size readers for #163" in the claude.ai project "symphony", 2026-10-26. Seven readings of public documentation and official client source, taken on 2026-10-25 and 26 with the sources listed at the end; the container's proxy refuses zenodo.org, huggingface.co, drive.google.com, api.kaggle.com and redivis.com, so what those five answer on the wire is taken from their clients' parsers, their tests and their documentation, and only PhysioNet's API was read live. Every byte count below is in bytes unless it says otherwise.

## The question

A downloader that must refuse a file which would not fit, before a byte of it lands, needs the file's exact size from its source. The official clients of the services below never refuse for lack of room: each reads a size, where it reads one at all, only to draw a progress bar, to decide whether to skip or resume a file, or to verify the download afterwards. So the refusal is the caller's, from one of the readings below, and the reading must also say how much the client will add to the disk, which depends on how the client names, resumes and overwrites what it writes.

## The generic HTTP way

Three readings, from the most reliable down (RFC 9110, June 2022, and RFC 9112 for HTTP/1.1).

1. A one-byte range request: GET with `Range: bytes=0-0` and `Accept-Encoding: identity`. A server that honours it answers 206 with `Content-Range: bytes 0-0/<total>`, and the total is the file's length (RFC 9110, sections 14.1.2, 14.4 and 15.3.7.1). A zero-length file answers 416 with `Content-Range: bytes */0`, which still states the size (15.5.17). A server may ignore the range and answer 200 with the whole body (14.2), so the reader checks the status, takes the 200's `Content-Length` only under the conditions of reading 3 and stops reading the body at once. On a 206 the answer's own `Content-Length` is the part's length, one byte, never the file's (15.3.7).
2. HEAD on the same address. The server should send the headers a GET would, but may leave out any it can only compute while sending the body, `Content-Length` being the RFC's own example (9.3.2); where it is present it must equal the GET's (8.6). Some signed storage addresses bind the method, so a HEAD can be refused where a ranged GET is not.
3. `Content-Length` on a 200 answer. It is the file's size only when there is no `Transfer-Encoding` (chunked transfer states no total and overrides any length, RFC 9112, sections 6.2, 6.3 and 7.1), no `Content-Encoding` (the length then counts the gzip bytes, RFC 9110, section 8.4), and the answer is the file and not a page sent in its place: a sign-in, consent or confirmation page carries a length of its own. A reader that sends `Accept-Encoding: identity` and checks the status and the `Content-Type` avoids all three.

The numerals are unbounded decimals (8.6, 14.1.2), so a reader bounds the digits it accepts rather than letting an integer wrap. The file can change between the reading and the download: a 206 carries the `ETag` or `Last-Modified` a 200 would (15.3.7), and `If-Range` on the download (13.1.5) makes a changed file come whole rather than as a mismatched tail. Whether a client forwards `Authorization` across a redirect to another host is the client's business: Python's requests strips it when the host changes, urllib re-sends every header of the first request to whatever host the redirect names, so a reader built on urllib refuses the redirect and reads the storage address with no credential of its own.

## Zenodo

- The listing: `GET https://zenodo.org/api/records/<id>`, no credential for an open record, else `Authorization: Bearer <token>` (the query form `access_token=` is documented as less secure). Its top-level `files` list carries, per file, `key`, `size`, `checksum` as `md5:<hex>` and `links.self`, which is `https://zenodo.org/api/records/<id>/files/<key>/content`. The size is the stored object's byte count, the same number the content endpoint sends as `Content-Length`; every file of a published record carries one, since the serializer reads it unconditionally. The InvenioRDM endpoints behind it, `/api/records/<id>/files` and `/api/records/<id>/files/<key>`, give the same `size` under `entries`.
- Two shapes exist: the deposition API, and records answered around the 2023 migration to InvenioRDM, say `filename` and `filesize` with a bare md5. A reader takes `size` or `filesize`, `key` or `filename`, and strips an algorithm prefix from the checksum, as zenodo_get does.
- A restricted or embargoed record answers 200 with `files: []`, not an error, so an empty list is not "nothing to fetch". Byte ranges are not promised: the files-rest layer's range support defaults to off, so a resuming download cannot count on a 206. Rate limits are 60 requests a minute for a guest and 100 signed in; one record request lists every file, so no per-file request is needed. `?download=1` belongs to the UI route `/records/<id>/files/<name>`, not to the API's content endpoint.
- The client, zenodo_get 3.1.0: streams each file straight into its final name with no temporary file and no rename, so a failed transfer leaves a truncated file under the real name, and a later run detects it only by recomputing the whole file's md5; a matching md5 skips the file, a mismatch re-downloads it whole over the old one (the default) or skips it; there is no byte-level resume. What a run adds is therefore each listed file's size, less nothing for a partial one, and the client puts the token in the query string of every request.

## The Hugging Face Hub

- The listing: `GET https://huggingface.co/api/<models|datasets|spaces>/<repo>/tree/<revision>?recursive=true`, paginated by a `Link: <...>; rel="next"` header (1,000 entries a page), `Authorization: Bearer <token>` for a private or gated repository. Each file entry carries `path`, `oid`, `size` and, for a file kept in LFS, `lfs.size`, `lfs.oid` and `lfs.pointerSize`: the top-level `size` is the real object's, equal to `lfs.size`, and the pointer is the hundred-odd bytes a clone without git-lfs would get. A `directory` entry carries no size the clients use, so a total is the sum over file entries only. `POST .../paths-info/<revision>` with up to 2,000 paths answers the same fields for chosen paths and silently leaves out one that does not exist.
- One file: HEAD on `https://huggingface.co/[datasets/|spaces/]<repo>/resolve/<revision>/<path>` answers `X-Linked-Size` with the linked object's size and `X-Repo-Commit` with the commit, redirecting an LFS or Xet file to a CDN; the client takes `Content-Length` only when the answer is not a redirect, sends `Accept-Encoding: identity` on the HEAD, and drops its `Authorization` header before following to another host. `X-Linked-Size` can be absent, and then the Python client's size is None and its dry run says "an unknown size".
- The client, huggingface_hub 2.3.0: `snapshot_download` lists the tree first and, with `dry_run=True`, returns every file's size and whether it would download, writing nothing; without it each file lands in a per-process temporary file named `<etag>.<8 hex>.incomplete` in the destination folder and is renamed into place, so the transient extra is one file per worker (8 by default); a blob already in the cache is reused and only a symlink is made; nothing resumes across calls in this version, and a failed call deletes its temporary file. A `local_dir` download writes real files with its bookkeeping under `.cache/huggingface/`. Plain HTTP refuses a file over 50 x 10^9 bytes unless the Xet client is installed. The CLI's human sizes are decimal (K, M, G at 1000 a step); compare bytes to bytes.

## Google Drive, through gdown

- There is no size-only request on the download host and the client sends no HEAD: the size is the `Content-Length` of the file's own GET, read once the answer's headers are in and before a body byte is read, and taken as the file's size only when both `Content-Encoding` and `Transfer-Encoding` are absent or identity. The address a file is served from is `https://drive.usercontent.google.com/download?id=<file id>&export=download&confirm=t&uuid=<uuid>`, with no key and no sign-in; gdown 6.4.2 never writes that host itself but copies it from the confirmation form.
- The chain: gdown asks `https://drive.google.com/uc?id=<id>`; an answer with `Content-Disposition` is the file; a 500 is retried at `/open?id=`; a Docs, Sheets or Slides page is switched to its `docs.google.com/.../export?format=` address; anything else is the virus-scan page, text/html with no `Content-Disposition`, about 2.4 KB, whose `Content-Length` is the page's. The page holds `<form id="download-form" action="https://drive.usercontent.google.com/download" method="get">` with hidden inputs `id`, `export=download`, `confirm=t` and a `uuid` minted for the page view; gdown copies every hidden input into the action's query and asks again. A reader copies them all, since derivatives that hard-code `confirm=t&uuid=` broke when the form changed. The Drive API's `files.get?fields=size` gives `size` as a string of bytes (absent for folders and shortcuts) under OAuth; whether an API key alone serves a link-shared file is not stated by Google's Drive pages.
- The client: the file is named from `Content-Disposition`; the body goes into `<output><random>.part` beside the final path and is moved over whatever is there, so the download occupies the disk once and a run without `--continue` ignores any earlier `.part` and starts another; `--continue` reuses exactly one; `--retries` reconnects with `Range` and `If-Range`. More bytes than announced, or fewer, raise an error and keep the `.part`. gdown's README says Google ends a connection after about an hour on a large file and throttles a widely shared one; the cookie jar it keeps under `~/.cache/gdown/` holds a whole google.com session and is sent to whatever google.com host the form names.

## Kaggle

- The listings: `POST https://api.kaggle.com/v1/competitions.CompetitionApiService/ListDataFiles` with `{"competitionName": ...}` and `POST .../datasets.DatasetApiService/ListDatasetFiles` with `{"ownerSlug", "datasetSlug", "datasetVersionNumber"}`, paged by `pageSize` and `pageToken`, each file with `totalBytes`. That is the per-file figure, and it is the extracted size: a large single file is served wrapped in a zip (a request for `foo.csv` lands as `foo.csv.zip`), and the whole-competition and whole-dataset archives have no listed size at all.
- The archive's size: `POST .../CompetitionApiService/DownloadDataFiles` with `{"competitionName"}`, or `.../DatasetApiService/DownloadDataset` with `{"ownerSlug", "datasetSlug", "datasetVersionNumber", "fileName"}`, `Authorization: Bearer <token>` (the KAGGLE_API_TOKEN form; a dataset listing and download run anonymously when no credential is found). The API answers a redirect to signed storage, which the client follows with `stream=True` and reads `Content-Length` from. A reader that wants the size without the body stops at the 3xx (no redirect following, so the token never leaves the API host), takes `Location`, and asks the storage address with a one-byte range; the signed address expires, after which it answers 403, so a size read long before the download needs a fresh POST. Whether the storage answers HEAD is unverified; the ranged GET is the safer probe.
- The client, kaggle 2.2.5: a whole competition lands as `<competition>.<extension of the redirect's path>`, in practice `.zip`; a whole dataset always as `<slug>.zip`; a single file under its own folders with the base name the redirect gives. Without `--force` it skips a local file that is at least as large as `Content-Length` and not older than `Last-Modified`, resumes a shorter one only when a sidecar `<file>.kaggle-partial` proves it is the same object (`Accept-Ranges: bytes` and the same validator and size), and otherwise rewrites it from byte zero; any failure in that check means download. No temporary file, no rename: an interrupted download leaves a partial file under the final name, which the sidecar marks. So the download adds at most `Content-Length` less what the file already holds, and a size mismatch at the end raises but keeps the file.

## PhysioNet

- Per version: `GET https://physionet.org/api/v1/projects/<slug>/versions/<version>/`, anonymous, 20 requests an hour (100 signed in), answers `main_storage_size` and `compressed_storage_size` as integers. `main_storage_size` is the sum of the version's file tree, computed after `SHA256SUMS.txt` is written and so including it, and excluding the zip; `compressed_storage_size` is the zip's, 0 until the background task that builds it after publication finishes, 0 once an editor removed it, and always 0 for a project kept in cloud storage, which also has no checksum file and no wget line. Both are public even for a credentialed project (verified live for a credentialed one on 2026-10-26). An editor who regenerates the checksums or the zip later recomputes both from disk, so the stated size can change under one version. The numbers on the HTML page are base-1024 labels; use the API's integers.
- Per file: the API lists no files. The nginx listing at `https://physionet.org/files/<slug>/<version>/<folder>/` shows each file's size in bytes, and a HEAD on a file answers its length, though HTTP basic authentication for a credentialed project is accepted only over HTTPS from a user agent starting `Wget/` or `libwfdb/`; anything else gets 403. `wget --spider --user <login> <url>` reads the password from `~/.netrc`, sends a HEAD, prints `Length: <bytes>` and downloads nothing; it prints `Length: unspecified` when the answer is gzip-encoded or carries no length.
- The client, the page's own `wget -r -N -c -np [--user <login> --ask-password] https://physionet.org/files/<slug>/<version>/`: lands everything under `physionet.org/files/<slug>/<version>/` (no `-nH`), writes `physionet.org/robots.txt` first because wget obeys robots by default, keeps one `index.html` per folder (the listings carry no `Last-Modified`, so `-N` refetches them every run), writes straight to the final names with no temporary file, resumes a shorter file by a `Range` from its on-disk size, re-fetches a newer one whole, and answers a local file longer than the remote with "already fully retrieved" and leaves it as it is. `-R 'index.html*'` makes wget delete each listing once it has read its links, so what stays is the version's files alone; the zip lives outside the version folder and is never fetched by the recursive command.

## Redivis

- Files held in a table: the client lists them with `GET https://redivis.com/api/v1/tables/<reference>/rawFiles?format=arrow`, `Authorization: Bearer <token>` when it has one, an Arrow stream with one row per file carrying `file_id`, `file_name`, `size` and `md5_hash` (base64); the client caches the listing for 30 seconds per table. This listing route is not in the public REST index, whose documented way to enumerate an index table, `GET /tables/<reference>/rows`, documents no size column; per file the public API documents `HEAD /api/v1/rawFiles/<file id>` with `Content-Length` and a `Digest: md5=` header.
- A tabular table as CSV: `POST https://redivis.com/api/v1/tables/<reference>/exports` with `{"format": "csv"}` creates an export job on the server; the export's `size` and `fileCount` are null until its `status` is `completed`, and the client polls `GET /api/v1/exports/<id>` until then and only after that reads `size`, the sum over the parts, before any part is downloaded. So the exact size is known before a byte lands, but only after the job has run server side, and the job cannot be cancelled or deleted through the public API; exports are quota-bound (100 GB a month unless the organization set its own egress), and whether creating one, or only downloading it, counts is not stated. The table's own `numBytes` from `GET /tables/<reference>` is the stored size, which the client uses only as a threshold, never the CSV's.
- The client, redivis-python 0.21.1: writes every file straight into its final name, `wb` first and `ab` on a resume, with no temporary file and no rename, so the disk cost is the final size and an interruption leaves a truncated file under the real name, which a later run does not continue: a file is skipped only where its size and md5 both match the listing, and otherwise rewritten in place with `overwrite=True` or refused. An export lands as `<table name>.csv`, or as parts `000000.csv`, `000001.csv` under a folder of that name when there are several. Downloads may redirect to signed cloud storage; requests drops the bearer token when the host changes, which a urllib reader must do itself. Without a token the client opens a browser for a device-flow sign-in and waits up to ten minutes, so an unattended run sets `REDIVIS_API_TOKEN`.

## Archives

- A zip states every member's name and uncompressed size in its central directory, read from the archive's tail without downloading it: the end-of-central-directory record is the last 22 bytes, or sits up to 65,557 bytes from the end behind a comment, and names the directory's size and offset; a zip64 archive puts them in a 56-byte record found through a 20-byte locator (PKWARE APPNOTE 6.3.10, sections 4.3.12 to 4.3.16, 4.4.8 and 4.4.9). Python's zipfile reads any seekable file object, so a file object whose reads are one-byte-range-then-range requests lists a remote zip with about two requests, and `infolist()` gives `file_size` for each member; the central directory is held in memory, nothing is written. Read the central directory, never the local headers, whose sizes are zero when bit 3 is set; a size of 0xFFFFFFFF means the zip64 extra field 0x0001 holds the true value; multi-disk archives are refused.
- A plain tar states each member's size in its 512-byte header, octal up to 8,589,934,591 bytes and beyond that in a pax `size` record or GNU's base-256 form, which Python's tarfile reads; but the headers are reachable only by walking the file, one range request per member, and the archive is larger than the sum of the sizes by its headers, padding and the two zero blocks at the end.
- A gzip-compressed tar states nothing usable: there is no index, a member's header is reached only by inflating everything before it, and gzip's ISIZE trailer gives the uncompressed total modulo 2^32 (RFC 1952, section 2.3.1), one per member of a concatenated stream, so an archive over 4 GiB cannot be sized from it. The practical bound before download is the archive's own length; what unpacking adds is known only once the archive has landed and can be inflated, so a reader decides a compressed tar twice, once for the archive and again for its members.

## What each client writes, which decides what a download adds

| Client | Temporary file | Resume | Existing file | What a run adds at most |
| --- | --- | --- | --- | --- |
| zenodo_get 3.1.0 | none | none | skipped on matching md5, else rewritten whole | each file's listed size |
| huggingface_hub 2.3.0 | `<etag>.<hex>.incomplete`, renamed | none across calls | reused when its blob is cached | each file's size, one transient copy per worker |
| gdown 6.4.2 | `<output><random>.part`, moved over | only with `--continue` | overwritten by the move | the file's length, plus any `.part` an earlier run left |
| kaggle 2.2.5 | none | with the `.kaggle-partial` sidecar | skipped when as large and not older, else rewritten | the archive's length less what is there |
| wget -r -N -c | none | from the on-disk size | skipped when no newer and same size | the version's files, plus `robots.txt` and the listings unless rejected |
| redivis-python 0.21.1 | none | within one run only | skipped on matching size and md5, else rewritten | each file's listed size, each export's stated size |

## Where the size is, in one table

| Source | Request | Field or header | Unit | Needs |
| --- | --- | --- | --- | --- |
| Any file server | `GET` with `Range: bytes=0-0` | `Content-Range: bytes 0-0/<total>` on a 206 | bytes | nothing, or the file's own credential |
| Zenodo | `GET /api/records/<id>` | `files[].size` | bytes | a token only for a restricted record |
| Hugging Face Hub | `GET /api/<type>s/<repo>/tree/<rev>?recursive=true` | `size` per file entry (`lfs.size` equal) | bytes | a token for a private or gated repository |
| Google Drive | the file's own `GET` on the usercontent host, after the confirmation form | `Content-Length` with identity encodings | bytes | nothing |
| Kaggle | `POST .../DownloadDataset` or `.../DownloadDataFiles`, not followed | a range request on the `Location` | bytes | the token, to the API host alone |
| PhysioNet | `GET /api/v1/projects/<slug>/versions/<v>/` | `main_storage_size` | bytes | nothing |
| Redivis | the files listing; `POST .../exports` then `GET /exports/<id>` | `size` per file; the export's `size` once completed | bytes | the token |
| A zip | two range requests on its tail | each member's `file_size` | bytes | the archive's address |

## Not verified here

- No answer from zenodo.org, huggingface.co, drive.google.com, api.kaggle.com or redivis.com was seen live; each shape above is what the official client parses and the documentation describes. Whether Kaggle's and Redivis's storage addresses accept HEAD, which md5 header Redivis sends on a file, whether a Drive HEAD or ranged GET answers a length, and whether a Zenodo content address answers a range were not exercised.
- The services change: Zenodo's file links moved at its 2023 migration, Drive's confirmation form has changed its inputs over the years, and Kaggle's client moved from REST paths to service paths; a reader that follows what the current client does, and refuses when the shape is not the one it knows, fails loudly rather than reads a page's length as a file's.
