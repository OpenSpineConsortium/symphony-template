# Artifacts on the grid, for every account

Source: the thread "Artifacts onto the grid", 2026-10-22, from the owner's message of 04:14 UTC: know the handoff docs/checkpoints/2026-10-22/export-artifacts-handoff.md and the skill it names, then automate as much as possible of putting the owner's claude.ai artifacts on the grid, so the owner can work on them from the other Claudes, across all six of the owner's accounts. It builds on that handoff, on the review beside it (export-artifacts-review.md) and on the multi-account design in grid-claude-accounts.md.

## What no workflow can do

An artifact belongs to the account that made it. The Artifact tool's listing with scope mine is the gallery of the account the session runs on, and another account's artifact reads only as a summary, so each account exports its own, from a session that runs on it: one `/export-artifacts <name>` per account, the one step no workflow takes, since a workflow has no claude.ai sign-in. Each account runs it once on its own artifacts, which hops no account to dodge a limit. After that, the rule of 2026-10-22 (docs/memory/artifacts-are-kept-as-files.md) has the session that makes a new artifact add it in the pull request of its work, so nothing has to be exported twice. A weekly routine on each account that runs the skill would catch an artifact a session forgot; it spends that account's usage on a schedule, so it is not made without the owner's word.

## The grid's copy: one folder for every account

Every account's grid worker runs as the one Unix account go2432, each account in its own Claude Code folder (grid-claude-accounts.md), so one folder serves all six: ~/claude-artifacts, mode 700, holding a clone of each repository whose artifacts/ is the only folder checked out (symphony-template/ and SchwingNet/), and a CLAUDE.md that tells a session there what the folder is. A per-account copy would hold the same files six times; the permission that matters is the Unix account's, not the Claude account's.

The folder is made and refreshed by hpcworker's gate word `artifacts` (tools/grid_gate.sh), a fixed word with no argument, sent through grid-accounts.yml's job action as every grid job is. It clones each repository the first time and afterwards only fast-forwards, refusing a clone that someone changed on the grid or that a group may write, as the gate's own clone is held; one refused clone leaves the other refreshed, and a clone the call began and could not finish is removed, so the next call starts it again instead of refusing it. The clones are the gate's, so the note in the folder tells a worker to read them and to make its edits in a clone of its own, by pull request, since a change in the gate's clone would stop its next fast-forward. symphony-template's .github/workflows/artifacts-grid.yml sends the word on every merge to main that changes artifacts/, every six hours as a fallback, and when started by hand; nothing in symphony-template sees a merge in SchwingNet, so the skill starts the workflow after one (its step 8). Where the gate's clone of hpcworker predates the word, the gate refuses it as a word it does not know, and the workflow sends `update` and asks again; any other failure fails the run as it came. The workflow runs only in symphony-template itself, never in a copy made from the template or a fork, and only while the repository is private, since a public repository's run logs are public.

The clone is made with `--no-checkout`, and with `--filter=blob:none` where git is 2.25 or later, so the grid downloads only the files it checks out; an older git, as the login node's may be, downloads every file and checks out the same. What is checked out is one sparse pattern, `/artifacts/`, written to the clone's own sparse-checkout file with cone mode off, since cone mode always checks out the files at the top of the repository, a CLAUDE.md among them, which a session started in the folder would read as instructions. Every fetch signs in through gh, set as the clone's only credential helper, so a helper of the grid account's own for another GitHub account is never asked; and git's own output never reaches the answer, which says only what was cloned, fetched and counted. The gate's tests check all of it, the old git's way and a checkout that fails included.

## Exporting a Claude Docs document exactly

Measured on this account's four Docs, 18,724 to 53,270 bytes as Markdown:

- Claude Docs read of the link lists the tabs and says how the doc is bound to its artifact, by publish or by grant.
- An export with a small maxBytes is refused as doc_too_large and gives the tab's real size in `got`, a cheap way to learn it.
- An export with no maxBytes came back inline for the three of 18,724, 21,990 and 26,657 bytes, as base64 with the length beside it. Copying that text by hand into a file is where a character is lost, so tools/docs_export.py reads the answer from the session's own transcript, where Claude Code keeps every tool result as it came, and writes it held to the stated length and to UTF-8; run on this session's transcript it wrote the three files byte for byte. Where the answer was saved to a file beside the transcript because it was large, it reads that file, only from the session's own tool-results folder; a subagent's large results are saved there too, not beside its own transcript under the session's subagents/ folder, as this session's review agent showed.
- The other way, which the export's refusal names for a large tab, saves the tab into the doc's own files: Claude Docs create with object blob gives an asset id and its sha256, and Artifact read with that id as path saves the file, whose sha256 matched. It worked on the doc bound by publish and was refused (forbidden, credential_rejected) on the three bound by grant, and it adds a file to the doc on claude.ai, which the owner sees, so the skill uses it only where the inline export is refused.

The four were sorted by the skill's search, all four to SchwingNet; one page of this account was held back by the skill's screen, since it holds other people's e-mail addresses, and waits for the owner's decision.

## What the review changed

An adversarial review of the first version found, besides the gate's faults above, that the skill could share a row whose folder was never copied, that its search for SchwingNet's subjects matched the organisation's own name in every file, that a published path was filtered only after it was read, that a republish under a new link would be copied twice, and that the workflow would ask for update after any failure. The skill now shares only a row whose folder is on main and left nothing out, and only where its search exits 1, having read everything and found nothing; the search passes over OpenSpineConsortium, adds the imaging words it lacked, and sends to SchwingNet any file it cannot read as words unless a look with Read shows nothing of the body; paths are filtered before any read and checked after the copy; a copy that matches a folder already kept gets a row linking that folder; records are read with ArtifactData's own out_dir, page by page, never under data/users/. The revised search still finds artifacts/symphony-handoff/ here, for 33 mentions of spine-program as a repository Symphony adopted and merges in, as this repository's own CLAUDE.md names it; it stays here, and the skill's sharing step leaves it private, since its search finds something.
