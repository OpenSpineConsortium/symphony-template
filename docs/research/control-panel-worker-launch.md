# Why a worker launched from the control panel did nothing, and what a grid worker's link opens

Source: the thread "Fix worker launch in control panel" in the claude.ai project "symphony3", 2026-10-25. The owner pressed Run the workers now for OpenSpineConsortium/SchwingNet and pasted the log of its Workers run #457, which printed `workers in Actions: []; this run: []` and ended green. The fix is OpenSpineConsortium/openspineconsortium.github.io#142.

## The launch

- .github/workflows/workers.yml runs only the registry's workers that say `"runs": "actions"` (tools/workers.py list --runs actions). SchwingNet's .github/symphony/workers/ held only its README on 2026-10-25, so the list was empty and the run ended in its first job, green, having done nothing. A run started by the schedule or a label ends the same way.
- The control panel's Run the workers now dispatched workers.yml without reading the registry, so nothing on the page said why. It now reads the registry first and, with no worker in Actions, says so and opens the Workers tab; a repository needs one worker file with `"runs": "actions"`, added by + Add worker (Where it runs: actions) and its pull request, and the secret CLAUDE_CODE_OAUTH_TOKEN, before a cloud worker can run there.
- A worker in Actions now has its own Run control (workers.yml dispatched with `worker` set), and a queued, given or blocker task has one that launches it: the task is given to a worker in Actions by its label, which wakes that worker at once (workers.yml's issues: labeled trigger), and a given task comes before the queue (docs/agents/PROTOCOL.md, Pick).
- Ordering the queue was not in the protocol: tools/sdlc_protocol/team.py deals the open issues by number, oldest first, after a worker's own claim and the tasks given to it. A priority the panel sets reaches the workers only through a change in symphony-protocol. The owner chose priority labels on 2026-10-25: OpenSpineConsortium/symphony-protocol#63 has the deal and the board take each of Pick's places labelled p1 first, then p2, then p3, then the issues with none, blockers still before the queue, and the panel's arrows put those labels on. It merged on 2026-10-25 with the version left at 0.6.1, so nothing was released: it reaches this template and the adopted repositories only with the next release of symphony-protocol, which is the owner's to make; until then giving a task to a worker is the way to put it first.

## What Open the session on a grid worker opens

- A grid worker is Claude Code run with Remote Control in a Slurm job (hpcworker's framework), signed in to one of the grid's Claude accounts: the slot kept to it, else the grid's current one. Its link is that Remote Control environment, `https://claude.ai/code?environment=env_...` (or a resumed session's own `https://claude.ai/code/session_...`), as docs/research/beethoven-worker-opening.md records.
- claude.ai shows an environment only to a tab signed in to the account that registered it, and a browser profile holds one claude.ai sign-in at a time (docs/research/beethoven-multi-account-workers.md). A tab signed in to any other account opens on that account's own claude.ai page, which is what the owner saw.
- The panel now names the account on the worker's line and offers Copy link, so the link can be opened in a browser profile signed in to that account, as Beethoven's one-profile-per-account design does.
- The owner then asked for the link to open straight in the Chrome profile signed in to that account, as a tab or else a new window. No web page and no extension can open a tab in another Chrome profile, and a window belongs to one profile; the one way code starts Chrome on another profile is a native helper (`chrome --profile-directory=...`), which needs the permission nativeMessaging, and Beethoven's CLAUDE.md forbids it since 16.0.0 removed the bridge that used it. Chrome's own Open link as, on a link's right-click menu, does it natively: it opens the link in the chosen profile's window, or a new window of that profile, and Chrome lists it once it has a second profile.
- So the Grid tab asks which grid account this Chrome profile is signed in to, kept in the profile's own localStorage as Beethoven's Settings keeps the same answer, opens a worker on that account with a plain press, and for a worker on another account says to right-click and choose Open link as, a plain press showing that instead of opening claude.ai on the wrong account (openspineconsortium.github.io#143). One-click switching would need that native helper, kept outside Beethoven; it was offered to the owner and not built.

## Open in Beethoven

- The owner then asked what Beethoven can do: a profile suggester from the session's id, and an Open in Beethoven entry on the right-click menu that starts on the right account, with no VPN and no grid sign-in needed. Beethoven 25.0.0 (OpenSpineConsortium/beethoven-extension#27) adds the permission contextMenus, which shows no install warning, and one entry on the links of each worker it last read online: Open in Beethoven for a worker on the account Settings names for this browser, which loads the link in the claude.ai tab Beethoven keeps, and a greyed line naming the account to pick under Chrome's Open link as for a worker on another. The workers are kept in the browser's storage.local and Chrome keeps the entries across restarts, so neither the grid nor the VPN is needed to use them. An extension still cannot open a tab in another profile, so the greyed line is the suggester.
- Chrome matches a match pattern against a URL's path and its query: measured on 2026-10-25 with Playwright and the session's preinstalled Chromium, a test extension's content script whose pattern ended `/code?environment=env_A*` loaded on `/code?environment=env_A1` and not on `/code?environment=env_B1`, `/code` or `/code/session_x`. A context menu's targetUrlPatterns take the same match patterns, so an entry built from a worker's environment link shows on that worker's links alone.
- The owner also found Beethoven's grid sign-in sheet replaced by "trying to connect to the grid" whenever the VPN was off. Beethoven 24.2.0 (OpenSpineConsortium/beethoven-extension#26, merged 2026-10-25) keeps its own sheet on screen with the reach in a line of its own, and the reach check runs in the background as before.

## The store release of 25.0.0

- Beethoven's main publishes to the Chrome Web Store on every merge (the variable CWS_ON_PUSH is publish), through OpenSpineConsortium/chrome-store-release-kit, which every caller takes at main. On 2026-10-25 the store refused the upload of 25.0.0.125 with HTTP 400 "You may not edit or publish an item that is in review." while 24.2.0.124 was in review: the store takes no upload while a review is under way. The kit's message then blamed the version, which was not the cause.
- The owner's rule, given that day: the older submission is withdrawn and the newer one submitted. The Chrome Web Store API V2 has the call for it, `cancelSubmission` (POST `v2/publishers/{publisher}/items/{item}:cancelSubmission`, an empty request and an empty answer), whose discovery document says it "can be used to cancel the review of a pending submission". fetchStatus names the version in review under `submittedItemRevisionStatus` (state PENDING_REVIEW, the version in `distributionChannels[].crxVersion`).
- chrome-store-release-kit#1 (merged 2026-10-25) reads a refused upload beside fetchStatus: where an older version than the zip's own is in review and the run submits, it withdraws that review, uploads once more and submits; a run that only uploads, a build not above the version in review, or a version it cannot read leaves the review alone. With CWS_ON_PUSH at publish, each merge therefore puts its own build in review in place of the one before, so frequent merges can keep a review from finishing; a repository that wants reviews to finish sets the variable to upload.
- On the rerun the same day, 24.2.0 was already out of review, so the store took 25.0.0.125 as the draft at once and nothing was withdrawn. The submit was refused with HTTP 400 "Your submission does not meet the requirements to be published in the store. Check the Developer Dashboard for steps to resolve.", which names no field. A new permission's justification is a field on the dashboard's Privacy practices tab that appears only once a package asking for the permission is uploaded (Beethoven's docs/store/SUBMISSION.md), so the first submit of a build that adds a permission is the owner's: paste the justification (docs/store/PASTE.md), Save draft, Submit for review.

## Several repositories at once

The panel kept one repository at a time behind a select. Every listed repository is now a tab, and the first tab, All, reads each one's open issues and running workers runs and sets them side by side (the same pull request).
