# Beethoven and Symphony: where they meet, measured

Thread "SchwingNet video demo plan", 2026-10-20. The owner asked whether Beethoven interfaces with the Symphony app, for a retraining of a model on the Wayne State grid that must run through Symphony's repository and Beethoven's research pipeline and gate, and said to make whatever the two need to fit. What follows is what was read and measured in that thread; the model and the study are the owner's private work and stay out of this note.

## What Beethoven is, on 2026-10-20

Three repositories under OpenSpineConsortium, depending in one direction, qa, then agents, then research (beethoven-research's CLAUDE.md, decision D2 of 2026-10-04):

- beethoven-qa 5.0.0: the definition of done (icontract on every public function, CrossHair with Z3 over them, pydantic at the boundaries, beartype on the hot paths), the gate as a command, the six code standards (readability, design, duplication, coverage, security, supply chain) as `python -m beethoven_qa standards`, a pinned copy that consumers carry under vendor/beethoven-qa with a kit of five files, and a Claude Code plugin.
- beethoven-agents: the image, the guard, the accounts and the super-master lease, the `claude -p` loop. Metaflow orchestration (D3) is not built.
- beethoven-research: the research pipeline. Built: one module, `beethoven_research.splits`, the split-level check (no evaluation case shares a patient, cadaver or source volume with a training case). Not built: the study record, the result row with n, interval, run id, commit and clean-tree flag, the reproduce-every-number command, the CLAIM checklist, the medical and telemetry stacks. Its CLAUDE.md names the first study: vertebral body detection on real fluoroscopy under domain shift, with its twelve open decisions the owner's (Linear BEE-181).

The launcher is hpcworker plus beethoven-extension; the template reaches the grid through hpcworker's runner chain (docs/setup/grid.md).

## What was measured

1. **The template's check with beethoven-qa vendored in.** beethoven-research's vendor/beethoven-qa (ORIGIN v3.0.0, 41 files) was copied into a clone of symphony-template at ae4990a, with the kit's three workflows and `.githooks/pre-push` in place, and `bash scripts/check.sh` run: 1142 tests, checks ok. The document check reads `.claude`, `docs`, `tools` and `.github` and never vendor/, so the copy's own files are outside its ASCII rule; actionlint and zizmor run only in CI, so whether the kit's workflows pass the template's zizmor settings is not yet measured here (beethoven-qa's own supply-chain group holds them to zizmor's regular persona).
2. **The collision.** Both ship `.claude/hooks/session-start.sh`: the template's fetches and prints the board, beethoven-qa's installs pixi and the locked environment in a cloud session. beethoven-qa's vendor-check requires every kit file in place and byte-equal to the copy's (`vendor.py`, `_check`), so a Symphony repository could not carry the kit without losing its board hook. Fixed in beethoven-qa 6.0.0 (this thread's pull request, pending until merged and tagged): the kit's hook is `.claude/hooks/beethoven-qa-session-start.sh`, the kit export at version 3. docs/setup/beethoven-qa.md is the order of steps for a Symphony repository.
3. **The code standards on a research pipeline as it stands.** beethoven-qa's `standards all --base none` (its source at 85f0e1c; ruff, radon, complexipy, bandit, lizard from PyPI; jscpd and zizmor not installed) over four tools of the owner's level-naming pipeline, 3,328 lines that have never been under a gate: 107 readability findings (functions of 100 to 310 lines, one with cyclomatic complexity 56), 2 design findings, 4 medium-severity security findings (three `torch.load` calls without `weights_only`, one fixed temp path), no contract on any public function. The reading for a retraining: the reported pipeline stays as the record, listed under `[tool.beethoven-qa.unproven]` with the reason that changing it breaks parity with the paper, and new code is written to the definition of done.
4. **The grid.** A training run through Symphony is one grid.yml dispatch on a chain started with a GPU: the GPU partitions at Wayne State take only the QoS gpu, gmsap is four nodes of four H200 each, galhp L40S, gvohp Tesla (the owner's infrastructure record of 2026-10-08); the chain's `--partition`, `--qos` and `--gres` size it at `--start`, and the job must end within the wall time less the margin. Whether the container is given the node's GPU (`--nv`) is still open in hpcworker's docs/OPEN_QUESTIONS.md; the first GPU chain is the test. A step never reaches Slurm itself, so a training that needs several nodes is several dispatches, each on its own chain; and since the container sees no lab volume, how the data reaches the node and where checkpoints go is open until the first GPU chain measures it.

## What follows

- A Symphony repository takes beethoven-qa 6.0.0 by docs/setup/beethoven-qa.md; scripts/check.sh runs the copy's vendor-check where pixi is on the path and says so where it is not.
- The reproducibility of a retraining comes today from the owner's own eval gate, model registry and locked environments, and from the split check; the engine's study record and result rows are not there to lean on, and a plan that says otherwise is wrong.
- Not yet measured: the kit's workflows under the template's zizmor settings; a GPU chain; beethoven-qa's gate on a GitHub runner for a repository with a research package of real size (its own package took 28 minutes of a 30-minute job on 2026-10-09).
