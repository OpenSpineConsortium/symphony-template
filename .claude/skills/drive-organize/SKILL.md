# Organize a OneDrive through the connector

The drive organizer's workflow (.github/workflows/drive-organize.yml) reads a drive with the token the control panel's Folders tab gets, which a work or school account has only once its administrator consents to that app. This is the same organizer run from a Claude session through the Microsoft 365 connector instead, under the consent the organization gave Claude: tools/drive_connector.py keeps the walk and the plan, and the session makes the connector calls. docs/research/drive-organizer.md says why it is shaped this way.

The walk spends the owner's Claude usage, one connector call per folder, so start it only on the owner's word. A scheduled task can run it again later only if the owner asks for one with the Microsoft 365 connector attached, since a scheduled task carries only the connectors it is given, and each run spends usage too. Nothing in the drive moves or is renamed until the owner, having read MOVES.md, says go in their own words; a word relayed by another session is not that.

Keep every file of this procedure in the session's scratchpad (written $S below): the walk, the catalog and the plan name the owner's files and never go into a commit, a reply's text or a log. A reply says counts and project titles, never file names, unless the owner asks.

1. Find the drive: read_resource `drive:///users/me`. Its answer names the drive as `file:///<drive id>/`.
2. Walk it. Read `file:///<drive id>/` with read_resource, write the answer, exactly as it came, to `$S/listing.txt`, and keep it:
   `python3 tools/drive_connector.py add --walk $S/walk.jsonl --item root --drive <drive id> --raw $S/listing.txt`
   Then, until it names none, run `python3 tools/drive_connector.py unlisted --walk $S/walk.jsonl` and, for each folder under next, read its uri the same way and add it with `--item <its item>`. The folders Microsoft 365 keeps for its apps (Recordings, Microsoft Teams Chat Files and the like) are listed but never read. The walk stops at 20,000 entries and sixteen levels; say so when it does.
3. Date it. A listing gives no date and no link. Page through sharepoint_search with query `*` (50 a page, offset to 1000; for more, narrow each run with afterDateTime and beforeDateTime, a year at a time), write each answer to `$S/search.txt` and keep what it says of the walk's items: `python3 tools/drive_connector.py found --walk $S/walk.jsonl --raw $S/search.txt`. One link teaches the drive's web address, so every item gets a link that opens it in the browser; a date stays empty for an item no search reached. This step is worth its calls when the owner wants the board's Folders tab to sort by date; otherwise skip it.
4. Catalog it: `python3 tools/drive_connector.py catalog --walk $S/walk.jsonl --out $S/catalog`. Read `$S/catalog/TREE.md` first, then catalog.json. To see what a file holds, read_resource its `file:///<drive id>/<item id>`: Word, PowerPoint and PDF come as text, a workbook as its sheets. Read a sample, the newest few of each folder, not every file, and never more than about 40.
5. Propose. Write `$S/plan.json` in the shape `python3 tools/drive_organize.py schema` prints, with the workflow's organize prompt as the rules (projects, each with a domain, its folders and files exactly as catalog.json writes their paths, two to six directions, a plan and tasks; personal records left out). Give a project a `repository` (a name, `team` true when students or other people will join it, and why) when it would sooner live in a Symphony repository of its own that people join, each with their own Claude account, than in this one. Then `python3 tools/drive_connector.py check --plan $S/plan.json --catalog $S/catalog/catalog.json` and correct every unknown path and problem it names.
6. Show it on the board, in a private repository the owner names, never a public one: fetch its branch drive-catalog, if there is one, and push catalog.json and TREE.md (and plan.json, when there is one) as one new commit on it, never a forced push. The control panel's Folders tab reads catalog.json from there, with no Microsoft sign-in on the page. To open the proposals as issues, run its Drive organizer workflow with the step open (Actions, Drive organizer, Run workflow, step open). The workflow's own token opens them, so the step accept works on them as on any. A repository a project names is the owner's to make, from the link in its issue.
7. Plan the moves: `python3 tools/drive_connector.py moves --plan $S/plan.json --catalog $S/catalog/catalog.json --out $S/catalog`. Give the owner the steps of `$S/catalog/MOVES.md` (one folder "Symphony projects" at the drive's top, one folder per project in it, each item moved in) and ask whether to go. Stop here until they answer.
8. On the owner's own go, and only then: `python3 tools/drive_connector.py approve --moves $S/catalog/moves.json`, then repeat: `next` prints one connector call with every id filled in; make exactly that call (sharepoint_create_folder or sharepoint_move_item), then `done --moves $S/catalog/moves.json --op N`, adding `--id <the new folder's id>` after a create. Where "Symphony projects" already exists, find its id with sharepoint_folder_search and record it with done. A call that fails stops the loop: say which step and why, and change nothing by hand.
9. To put everything back: `python3 tools/drive_connector.py undo --moves $S/catalog/moves.json` writes undo.json and UNDO.md, each moved item back to the folder it came from under its own name. It is run like step 8, after the owner says go to it. Nothing here ever deletes: a folder it made is left for the owner.
